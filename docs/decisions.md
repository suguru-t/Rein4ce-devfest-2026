## サーバ（C）

### 1. タワーの保存先を Firestore にする 〔決定〕2026-11-06

**背景**：最初はサーバのメモリに保存していた。Cloud Run はインスタンスが入れ替わる・複数立つので、送ったタワーが消えたり、見る人によって「みんな」の一覧が違ったりする。デモ中に起きると致命的。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Firestore（採用）** | サーバレスで Cloud Run と相性がよい。サービスアカウントで接続でき鍵ファイル不要。無料枠で足りる | 一覧の並べ替えや件数に、クエリの書き方の工夫が要る |
| メモリのまま | 何もしなくてよい | 再起動・スケールで消える。デモで事故る |
| Cloud SQL | SQL で自由に集計できる | 常時起動で料金がかかる（クレジットが少ない）。設定が重い |
| Cloud Storage に JSON を置く | 単純 | 一覧・新しい順の取得が面倒。同時書き込みに弱い |

**理由**：開発前の方針（PDF 2 章）でも Firestore と決めていた。実装してみて、ルートやアプリ側を変えずに置き換えられることを確かめた。

### 2. Firestore には「タワー全体の JSON」と「一覧用の項目」を両方持たせる 〔決定〕

**決めたこと**：1 タワー 1 ドキュメント。`json` フィールドにタワー全体（`:core` の `Tower` をそのまま文字列化）を入れ、一覧用に `height`・`partCount`・`createdAt`・`author` も別に持つ。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **JSON ＋一覧用の項目（採用）** | 形式の正が `:core` の 1 か所だけ。`Part` に欄が増えてもサーバの変更が要らない。一覧は軽い項目だけ読める | Firestore のコンソールでパーツの中身が読みにくい |
| 全部を Firestore の項目に分解 | コンソールで見やすい。中身で検索できる | `Part` を変えるたびにサーバの変換コードも直す必要があり、ずれやすい |

**理由**：データ形式はチーム全員で守る約束（README「データ形式」）なので、変換の書き直しが起きる場所を増やしたくなかった。パーツの中身で検索する予定はない。

### 3. 保存先は環境で自動的に切り替える 〔決定〕

**決めたこと**：Cloud Run 上（環境変数 `K_SERVICE` がある）では Firestore、手元ではメモリ。`TOWER_STORE=firestore|memory` で明示もできる。テストは必ずメモリ版を使う。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **自動切り替え（採用）** | gcloud を入れていないメンバーの手元でも今までどおり動く。本番は設定なしで Firestore | 「今どっちで動いているか」が分かりにくい → 起動ログに `TowerStore: ...` を出して対策 |
| いつも Firestore | 本番と手元が同じ | 全員に gcloud と認証が必要。テストが本物につながってしまう |
| Firestore エミュレータ | 本物に近いものを手元で使える | 準備（Java 版エミュレータの起動など）が全員に要る |

**理由**：4 人それぞれの手元の環境をそろえる時間がハッカソンにはない。サーバ担当以外がサーバを動かすときに詰まらないことを優先した。

### 4. 命名（Gemini）は Vertex AI 経由で呼ぶ 〔決定・実装中〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Vertex AI（サーバから呼ぶ。採用）** | ハッカソンのクレジットの対象。サービスアカウントで認証でき、API キーがアプリに入らない | GCP の設定（API 有効化・権限付与）が要る |
| AI Studio（Gemini API キー） | 設定が簡単 | **クレジットの対象外**。キーの管理が要る |
| アプリから直接呼ぶ（Firebase AI Logic など） | サーバを経由しない分速い | アプリに Firebase SDK を入れない方針（PDF 2 章）に反する |

**理由**：クレジットの対象かどうかが決め手。サーバ経由なら、失敗してもアプリ側の動きを変えずに済む。

### 5. 命名を付けるタイミングと担当 〔決定〕チームで相談

**決めたこと**：採集が終わった直後に自動で付ける。API を呼ぶのは A（採集画面）、名前をパーツに保存するのと、手持ち画面の「名前を付ける」ボタン（付け直し）は B、API は C。

**理由（B の意見）**：「パーツができました」の画面で名前が出るのが一番楽しく、デモで見せやすい。ただしパーツはすぐ出して、名前は届いたら差し替える（届くまでは「名前を考え中…」）。

**実装（2026-11-07）**：A が作業できなくなったので、A の分（採集画面から API を呼ぶ）も B が作った。
- 採集の直後：結果のダイアログに「名前を考え中…」と出し、名前が届いたら保存して差し替える。付かなければ「○ m の散歩」のままにして「名前はコレクションから・あとで付けられます」と添える（7）。届くまでのあいだに自分で名前を付けていたら、そちらを残す
- コレクションの「名前を付ける」：「AI に考えてもらう」で AI の案を入力欄に入れる。保存するか・直すかは自分で決める
- 送るのは形・距離・日時だけ。今付いている名前も送らない（8）。本番のサーバで 10 回試して、どれも 1 秒ほどで返った

### 6. 命名は「名前だけ」にする（一言コメントは付けない） 〔決定〕チームで相談

**開発前の方針（PDF 4 章）からの変更**：PDF では「名前と一言」を返す予定だった。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **名前だけ（採用）** | `Part` の形を変えずに済み、全員への周知が要らない | AI らしさは少し弱まる |
| 名前＋一言 | デモで「AI が道に物語を付けた」と見せられる | 手持ちのカードが狭く、一言が入りきらない（B の指摘） |

**理由**：表示する場所がないものを作っても意味がない。一言は、あとから `Part` に空でもよい欄として足せば今までのデータもそのまま読めるので、余裕があれば後でやる。

**AI の提案との関係**：Claude Code は最初「名前だけ」を勧め、次に「`comment` 欄を足しておくのが安い」と提案を変えた。最終的には B が画面の都合から「名前だけ」を選んだ。

### 7. 命名に失敗したら 503 を返す（代わりの名前は返さない） 〔決定〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **503 を返す（採用）** | アプリは「失敗した」と分かるので、今の表示（例：「341 m の散歩」）を残し、あとで付け直せる | アプリ側に失敗時の処理が要る |
| 代わりに種類名（「ジグザグ」など）を名前として返す | アプリは何も考えずに表示できる | アプリはそれを本物の名前だと思って保存してしまい、付け直しのきっかけがなくなる |

**AI の提案との関係**：Claude Code の最初の計画は「失敗したら種類名を返す」だった。B の「失敗したら今の表示のままにして、ボタンで付け直す」という案を受けて、代わりの名前を返すと付け直しの流れが壊れることに気づき、503 に変えた。

### 8. 名前の手がかりは形・距離・日時だけ。地名は入れない 〔決定〕チームで相談

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **形・距離・日時だけ（採用）** | 位置情報がサーバに出ない（PDF 5 章のルールのまま） | 「駅前の〜」のような名前は付けられない |
| スマホ側で町名に変えて送る | 場所らしい名前が付く | 名前は共有ページ（誰でも見られる）に載るので、どこを歩いたか・どこに住んでいるかの見当がつく |
| 生の GPS をサーバに送る | 何でもできる | ルール違反。プライバシーの問題が一番大きい |

**理由**：名前は共有ページや「みんな」の一覧に出る。地名が入ると、歩いた場所が他人に知られてしまう。B が「場所を入れるならルールを変える話になる」と指摘し、今回は入れないと決めた。

### 9. 命名の安全策：3 秒で打ち切り、10 文字まで、変な入力は 400 〔決定〕

- **3 秒で打ち切る**：アプリの「名前を考え中…」が長すぎないように。時間切れは失敗（503）
- **10 文字まで**：手持ちのカードに収まる長さ。Gemini は指示より長く返すことがある。**追記（2026-11-07）**：当初はサーバで切り詰めていたが、「夕暮れの七曲りブロッ」のように言葉の途中で切れた名前が出た（#53 で B が発見）。今は、指示文で「8 文字くらい、長くても 10 文字」と余裕を持たせ、それでも超えたら前の案を見せて 1 回だけ聞き直し、まだ長ければ切り詰めずに 503（アプリは「○ m の散歩」のまま。コレクションからやり直せる）。文字数は絵文字も 1 文字と数える
- **頂点が 0 個・50 個超のパーツは 400**：変換結果は 12 個程度だが、ぴったり 12 で切るとアプリ側の変換が少し多いだけで弾かれる。Gemini に大きなデータを送らないための歯止めとして、明らかにおかしい量だけ弾く
- **命名の部品（`PartNamer`）を差し替えられるようにする**：テストでは本物の Gemini を呼ばない（お金がかからず、結果が毎回同じ）。gcloud がない手元では「命名なし（503）」で動く

### 10. Gemini のモデルは `gemini-3.5-flash-lite`（global） 〔決定〕2026-11-06 試し打ちで決定

**最初の予定からの変更**：最初は `gemini-2.5-flash` を使う予定だった。実際に呼んでみて、次の結果で替えた。

| モデル（場所） | 結果 | 判断 |
|---|---|---|
| `gemini-2.5-flash` | このプロジェクトでは **404**（モデル一覧には出るが、新しいプロジェクトからは使えない）。東京・global・米国どこでも同じ | 使えない |
| `gemini-3.8-flash`（global） | 1.5〜20 秒。英語の返事や空の返事が混ざる | 遅く不安定 |
| `gemini-3.5-flash`（東京） | 空いている時間は 0.7〜1.2 秒で名前もよい。**混む時間は 5〜8 秒、429（混雑）も返した** | 時間帯で揺れる |
| **`gemini-3.5-flash-lite`（global。採用）** | **12 回とも 0.8〜1.5 秒**。名前の質も十分（「黄昏の折り目」「初夏を刺す直進」「冬夜のループ」） | 採用 |
| `gemini-3.1-flash-lite`（global） | 速いが、10 文字を超える・記号が混ざることが多い | 不採用 |

**理由**：命名は短い仕事なので、大きいモデルの賢さより、**いつ呼んでも 3 秒以内に返ること**を優先した。3.5-flash-lite は東京にはなく global でだけ使えるが、それでも 1 秒前後で返る。

**呼び方**：
- 考える時間（thinking）は最小（`MINIMAL`）。長く考えさせると 3 秒を超える
- 返事は JSON（`{"name": "..."}`）に固定して、読み取りを安定させる
- 温度は 1.0。1.8 に上げても名前のばらつきはあまり増えなかった。代わりに指示文に「ありがちな名前は避け、意外性のある言葉選びにする」を足した（同じ特徴の散歩に毎回同じ名前が付くのを減らすため）
- 日時は日本時間の季節（「晩秋」など）と時間帯（「夕方」など）に直して渡す
- モデルと場所は環境変数（`GEMINI_MODEL` / `GEMINI_LOCATION`）で替えられる。混雑の状況が変わったら試し直す

**途中で外れた仮説**：最初、「サーバ経由だと起動直後だけ遅い」と考え、起動時に準備の呼び出しをする仕組みを入れた。ところが同じ時間に直接呼んでも遅く、遅かったのは **Gemini 側の混雑**だったと分かったので、その仕組みは取り除いた（教訓は 12 番と同じ：比べる相手を用意して確かめる）。

## 開発の進め方

### 11. main には直接入れず、PR とレビューを通す 〔決定〕チームの約束

**決めたこと**：作業ごとにブランチを切り、PR を作って、D（GitHub: mintBomber）にレビューしてもらってからマージする。PR では GitHub Actions がビルドとテストを自動で確認する。

### 12. 確認は「本当にそこにつながっているか」まで見る 〔教訓〕

Firestore 版を手元で試したとき、前に起動したサーバのプロセスが止まりきらずに残っていて、リクエストが**古いメモリ版に届いていた**。応答は正常に見えたので、気づかずに「動いた」と判断しかけた。

**対策**：起動ログに保存先（`TowerStore: FirestoreTowerStore`）を出すようにした。確認のときは、Firestore 側にも本当にデータが入ったかを別の方法（REST API）で見る。

## 変換・コレクション（B）

### 13. パーツは「分類した型」ではなく「歩いた形そのもの」で見せる 〔決定〕2026-11-06（#8）

**背景**：パーツの形はもともと軌跡の頂点から作っていて、物理もその形で動いていた。ただ、簡略化が粗く（15 m 未満の曲がりは無視、角は最大 12 個）、名前のないパーツを「U字」などの分類名で呼んでいたので、「型に当てはめられた」ように見えていた。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **歩いた形そのもの（採用）** | 自分が歩いた道だと分かる。同じ L 字でも 1 本ずつ形が違い、集める楽しさになる | 頂点が増える（上限 12 → 24 個）ので、物理の部品も増える |
| 棒・L字・U字…の型に当てはめる | 形がそろうので、積みやすさを調整しやすい | どこを歩いても似た形になり、歩いた意味が薄れる |

**決めたこと**：
- 簡略化の ε を 15 m → 8 m、頂点の上限を 12 → 24 個にした（`ConversionParams`）
- 名前のないパーツは、分類名ではなく「341 m の散歩」のように距離で呼ぶ（`Part.displayName`）
- 分類は名札と色にだけ使い、以前と同じ粗さ（15 m・12 個）で判定する。形を細かく残しても、分類と色は変わらない
- そのため、最初の予定にあった「分類（`classify`）の精度を上げる」は優先度を下げた

**理由**：B が「型に当てはまるより、歩いた形がそのまま出る方が面白い」と考えた。合わなければ戻せるように、細かさと呼び名を別々のコミットにして出した。頂点の上限はチーム共通のデータ形式なので、PR で全員に影響を書いて伝えた（D は物理の部品が増える、C はサーバの変更なし）。

### 14. 簡略化の細かさ（ε）を GPS の精度に合わせて変える 〔決定〕2026-11-06（#13）

**背景**：#8 のレビューで A から「ε 8 m だと、GPS の揺れで形がギザギザにならないか」と聞かれた。机の上で考えるより実データで確かめることにして、B が iPhone で 7 本歩き、アプリと同じ処理（`TrackFileParser` → `TrackToPart`）で変換して比べた（200 m 未満でパーツにならない 1 本を除く 6 本）。

| 案 | 結果（頂点の数） | 判断 |
|---|---|---|
| ε 8 m 固定（#8 のまま） | 精度が良い 5 本（±2.5〜3.4 m）はギザギザなし。GPS が粗い 1 本（±17〜24 m）は 16 個で、揺れが絡まる | 粗い記録に弱い |
| ε 8 m ＋ 位置を 8 m ごとに間引く | 揺れの分だけ距離が短く測られ、201 m の散歩が 200 m を割って**パーツにならなくなった**。頂点もかえって増えた（16 → 18 など） | 逆効果 |
| **ε ＝ 8 m と「使う点の精度の中央値」の大きい方（採用）** | 精度が良い 5 本は #8 と**まったく同じ**。粗い 1 本だけ 16 → **9 個** | 採用 |

**理由**：精度が良い記録の形はそのまま残し、粗い記録だけを大まかにまとめられる。精度が分からない点（GPX など）は数えず、全部分からなければ基準の ε のまま。比べた結果の表と画像は #8 のコメントにある。
**そのあとの変更**：基準の ε は、A の調整（#15）で 8 m → 10 m になった。
**位置情報の扱い**：歩いたデータはリポジトリに入れていない。比べるときも、場所を千住キャンパスに移したデータだけを共有した（自宅の近くが分からないように）。

### 15. コレクション画面の見た目は「測量野帳」 〔決定〕2026-11-06（#17）

**背景**：標準の部品のままだと、どのアプリにもある見た目で「AI で作った感じ」が出ていた。このアプリらしい見た目にしたかった。

実際のデータで 3 案を描き比べた。

| 案 | 特徴 | 判断 |
|---|---|---|
| 標本箱 | 博物館の標本のように、形を墨一色で並べる。採集番号と日時のラベル | 世界観は伝わるが、選ばなかった |
| **測量野帳（採用）** | 方眼紙に、地図の道路のような縁取りの線で描く。縮尺（実際に歩いた距離から計算）と北を入れ、「本当に歩いた道」だと分かるようにする | B が「可愛い」と感じた |
| 積み木 | パーツを色付きの立体の積み木に見せる。ゲームらしく楽しい | いちばん「よくあるゲームアプリ」に寄りやすい |

**理由**：縮尺と北を入れると「歩いた形そのもの」（13）が引き立つ。道の形と太さは物理と同じ `PartGeometry` で描くので、積む画面での当たり判定とも一致する。
**そのあと（#21）**：北の印を赤い方位磁針の針にした。パーツは 1 本ずつ白い紙片に載せて、隣との境目を分かりやすくした。アプリ全体を野帳にそろえる案は、チームで相談中（A は賛成）。

### 16. 並べ替えは、iPhone のホーム画面と同じ操作にする 〔決定〕2026-11-06（#20 → #21）

**経緯**：最初（#20）は、長押しのメニューで「先頭へ」を選ぶ形にした。ドラッグはタップ（選ぶ）や長押しとぶつかりやすく、作る手間もかかると考えたため。B が使ってみて「ドラッグで好きな場所に置ける方が便利。iPhone のアプリを移動させるときの感じにしたい」と判断し、作り直した（#21）。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| 長押しのメニューで「先頭へ」（#20） | 作るのが簡単。タップとぶつからない | 好きな場所に置けない。並べたい順にするには、何度も「先頭へ」を押す |

### 20. 歩き以外（車・自転車・走り）はパーツにしない 〔決定〕2026-11-07

**背景**：このアプリは「歩いた道」を集めるものだが、車や電車で移動しながら記録しても距離の長いパーツができてしまう。A が「歩きのときだけに限定したい」と考えた。

**決めたこと**：GPS の点列を 30 秒の窓で見て（窓の始点から終点までの直線距離 ÷ 時間）、時速 8 km（2.2 m/s）を超える区間が 1 つでもあれば「歩くより速い移動がありました」としてパーツにしない（`TrackToPart.Result.TooFast`）。記録中も最近 30 秒の速さを見て、超えていれば状態行で「速すぎます」と知らせる。

**理由**：
- 歩きは時速 4〜6.5 km、走りはゆっくりでも時速 8 km 以上なので、その間に線を引いた。自転車（時速 12 km〜）や車は確実に弾ける
- 点と点の間の速さは GPS の揺れでばらつく（既にある「飛び」の上限 5 m/s はその対策）ので、30 秒の窓で見る。信号で止まる・横断歩道を小走りで渡る程度では弾かれない
- 窓の中は、点をたどった道のりではなく始点と終点の直線距離で測る。道のりだと粗い GPS の揺れが全部足されて、歩きでも走りに見えてしまう（テストで ±6 m の揺れを入れると 2.2 m/s を超えた）。直線距離は曲がった分だけ少なめに出るが、車や走りは 30 秒で歩きの数倍は進むので十分に分かる
- 速い区間だけ切り取って残す案はやめた。切った前後がつながって、歩いていない直線が形に入ってしまうため
- 時刻の分からない点が混ざった軌跡（GPX の一部）は判定しない。今までどおりパーツになる

**AI の提案との関係**：上限の値と「30 秒の窓」は Claude Code の案。最初は道のりで測る実装だったが、既にあった粗い GPS のテストが「走り」として弾かれて気づき、直線距離に変えた。A の「歩きだけ」という方針を受けて、走りとの境目をどこに置くかを歩き・走りの一般的な速さから決めた。実機で歩いてから調整する。

**追記（2026-11-07 同日）**：A が自分で走って録った 2 本（最高 時速 8 km と 12 km）を流したところ、どちらも弾かれた。A は「ジョギングは通したい」と決め、上限を時速 8 km（2.2 m/s）から **時速 14 km（3.9 m/s）** に上げた。自転車の巡航（時速 15 km 以上）と車は弾けるが、ゆっくりの自転車は通る。
あわせて、**記録中に上限を超えたら自動で記録を止める**ようにした（`TrackRecorder`。画面を閉じていても効く）。速かった最後の 30 秒を切り落とし、そこまでの分がパーツにできる長さならパーツにする（歩いてから電車に乗った、のような場合に歩いた分を無駄にしないため）。短ければ「短すぎてパーツになりません」と出す。
この判定では飛びのフィルタ（5 m/s）を通さない。車のように速い点は飛びとして全部落とされて、速さが測れなくなるため。
そのぶん、1 点だけの GPS の飛び（B が 11/6 の歩きに 90 m の飛びを 1 点入れて試したところ止まった。#47 のレビュー）で止めないよう、上限を**超えた状態が 10 秒続いたら**止めることにした。自転車や車は超え続けるので 10 秒遅れて止まるだけで、1 点の飛びは次の点で元に戻るので止まらない。切り落とす位置は「超え始めた時刻の 30 秒前」。

### 21. 歩いたときの天気で、道の色と背景を変える 〔決定〕2026-11-07

**背景**：B が「歩いた天気で、方眼紙の上に雨を降らせたい（天気アプリのように）。雨の日の道は青くしたい」と考えた。

**決めたこと**（どれも B が選んだ）：

| 決めること | 選んだもの | ほかの案 |
|---|---|---|
| 天気を持つ場所 | スマホの中の別ファイル（`parts_weather.json`）。B だけで作れる | `Part` に足す（積む画面や共有ページでも使えるが、全員の合意が要る）。あとで移せる |
| 背景に出す天気 | 見ている画面に合わせる（採集＝今の天気、コレクション＝大きく見ているパーツ、見ていなければ最後に歩いたパーツ。積む・みんなは出さない。→ #64 で「みんな」にも採集と同じ今の天気を出すようにした。聞き直しは `WeatherService` が 15 分以内なら抑えるので増えない） | 最後に歩いた天気だけ／今いる場所の天気だけ |
| 描く場所 | 方眼紙の上、画面の部品の下（字やボタンの邪魔をしない） | いちばん上にうすく重ねる |

- 天気は Open-Meteo（キー不要・無料）から取る。送る位置は 0.1 度（約 10 km）に丸め、歩いた正確な場所は外に出さない
- 道の色：雨のなかまは青、雪は水色、くもり・霧は灰色、晴れはいつものオレンジ。白い紙片の上で形が見えるよう、縁取りはどれも濃くする
- → 2026-11-08（#69）：色だけでは天気が分かりにくいので、パーツの図の左上（右上の北と対になる位置）に天気のアイコン（太陽・雲・霧の線・雲と雨・雲と稲妻・雪の結晶）を出す。アイコンは道と同じ色。道の中に天気の模様（雨の筋・雪の粒・雲のかたまりなど）を重ねる案も試したが、小さいカードでは何の柄か分かりにくかったので、B が見てアイコンにした
- 晴れは天気アプリの晴れの画面に寄せた（空の色、白く飛んだ太陽、ごくうすい虹色の輪、六角形のきらめき、傾けると動く）
- 天気データの出どころ：Open-Meteo のデータは CC BY 4.0 なので、コレクションの拡大表示で天気を字で出すところに「天気データ：Open-Meteo.com（CC BY 4.0）」を添える（リンク付き）。見本の天気は作り物なので付けない
- 電池：背景はずっと動くので、描き直しを抑える。ゆっくりな空（くもり・霧・晴れ）は 1 秒に 30 回、雨・雪は 60 回まで（1 秒に 120 回描ける機種でもそれ以上は描かない）。背景だけを別の層にして方眼紙は描き直さない。傾きはセンサーが変わるたびでなく、描き直すときに入れる。記録中（採集画面を開いたまま歩くことが多い）は、どの画面でも止まった絵にして傾きのセンサーも止める（A のレビューより）。エミュレータ（GPU あり）で、雨・雪の引っかかり（描くのが間に合わないコマ）は 3〜17% → ほぼ 0%、CPU は 35〜116% → 約 22% になった

**経緯**：晴れの太陽は 5 回作り直した。扇形の光の筋 → 左上の光とレンズのきらめき（太陽と分かりにくい）→ 黄色い円盤と光芒（輪の主張が強く不自然）→ 縁のない白い光 → 空の色と虹色の輪。曇りの雲も「はっきりした雲」を試したあと、最初のふんわりした雲に戻した。雪の道の色は、白い紙片と同化して見えにくかったので濃い縁取りにした。

**AI の提案との関係**：描き方（雨粒の奥行き、霧で方眼の線を隠す、傾きで動かす など）は Claude Code の案。どの見た目を採るかは、B がエミュレータで見て毎回決めた。

### 22. 「みんなのタワー」の一覧は、アプリを立ち上げたときに先読みする 〔決定〕2026-11-07

**背景**：アプリを立ち上げてすぐ「みんな」を開くと「サーバから読み込み中…」を 5 秒ほど見ることがあった。

### 23. POST /towers は保存前に検査して、壊れたタワーは 400 で断る 〔決定〕2026-11-07

- 起動画面の動き：最後の「ミ」が右の外から回りながら落ちてきて、止まる位置の少し右に着き、左へ弧を描いて 1 回はねて収まる（はね上がる速さは落ちる速さの半分ほど）。一瞬（0.3 秒）置いてから、積み木の門の形の穴をくぐって採集画面に入る。準備が速い端末では起動が長くても 0.65 秒延びる

- 下のタブ：選んだタブの後ろの灰色の丸を 1 つにして、タブを切り替えると横にすべって動くようにした

**やらなかったこと**：アプリ全体の画面のなめらかさ（リフレッシュレート）の設定。端末の設定で決まる部分が大きく、エミュレータ（60 Hz まで）では確かめられないため

**AI の提案との関係**：設定の項目の案（ニックネーム・天気の背景の動き・画面を消さない など）と、起動画面を 1 枚の絵にまとめる方法は Claude Code の案。どの見た目・速さにするかは、B がエミュレータで見て毎回決めた（はね方は「真上は不自然」「1 回で収めたい」など何度も直した）。

### 25. 採集画面の題字「ミチツミ」を押すと動く 〔決定〕2026-11-07

### 26. コレクションの見出しの字の下に、紙の色を敷く 〔決定〕2026-11-07

### 28. パーツの注記は「足跡のマーク 長さ・日付・天気」にし、変換の数字は出さない 〔決定〕2026-11-07

### 29. 端末の言語によらず、字を日本語として描く（#46） 〔決定〕2026-11-07

### 32. 自分のタワーは「持ち主の印」（端末の id のハッシュ）で見分ける 〔決定〕2026-11-07

**背景**：設定でニックネームを付けられるようになったが、名前はただの文字列で、同じ名前の人が 2 人いても区別できない。「みんな」で自分のタワーに「あなた」の札を出したいが、サーバには利用者を見分けるものが何も無かった。ログイン（Google アカウントなど）はハッカソンの残り時間では重い。

**決めたこと**（C）：
- アプリが端末ごとに「持ち主の印」を作る：端末の `ANDROID_ID` にアプリだけの塩を付けて SHA-256 にした 64 桁の 16 進（`data/OwnerId`）。元の id はサーバに送らない。Android 8 以降は同じ署名なら入れ直しても同じ値なので、アプリを消しても札は残る。端末を替えると変わる
- 送るタワーに `ownerId` として入れ（`Tower` に任意の項目を 1 つ足した。古いアプリは送らないので null）、一覧を取るときはヘッダ `X-Owner-Id` で送る
- サーバは印を保存するが、**どの応答にも印を入れない**。一覧は各タワーに `mine: true/false` を付けるだけ、1 基の JSON では null にして返す。返すと、同じ人のタワーを誰でもたどれてしまうため
- 形が違う印（64 桁の 16 進でない）は、送信では 400、一覧のヘッダでは無いものとして扱う
- 送信できた id はスマホの中にも残す（`data/MyTowers`）。サーバが落ちていても札が出る保険

**印の元を `ANDROID_ID` にした理由と、気をつけること**（#66 のレビューで kkambayashi が指摘）：
- Android の指針では、見た目だけの用途にはアプリの中で作った乱数の id が勧められている。乱数にすると、アプリを消して入れ直したときに「あなた」の札が消える（`allowBackup="false"` のため）
- それでも `ANDROID_ID` を元にしたのは、「入れ直しても自分のタワーが分かる」ことを C が優先したため。印はハッシュで、元の id はサーバに届かない。サーバの中では、同じ端末のタワーが同じ印でつながる（Firestore を見られる人には分かる）。札は見た目だけで、消す・直す権限には使わない
- 利用者が印を消す手段は無い。「アプリについて」の「外に送るもの」に、この印を送っていることを書いた（#66）
- 乱数の id に切り替えるなら `data/OwnerId.kt` の元の値を変えるだけで、サーバは変えなくてよい。チームで決め直すならここ

**やらなかったこと**：ログイン（時間と、位置を扱うアプリにアカウントを結び付けたくない）。印を一覧に返して端末側で比べる案（上の理由で返さない）。ニックネームで比べる案（同じ名前を区別できない）。

**AI の提案との関係**：印をハッシュにして送る・一覧には真偽だけ返す、という設計は Claude Code の案。ログインまではしないこと、入れ直しでも残る `ANDROID_ID` を元にすることは C が決めた。

### 33. 夜は太陽の代わりに月を出す（ふだんは三日月、満月の夜だけ満月） 〔決定〕2026-11-08

**背景**：背景の天気は、晴れなら昼でも夜でも太陽を出していた。夜に歩いたパーツを見たときや、夜にアプリを開いたときも太陽が出るのはおかしい、と B が気づいた。

**決めたこと**（B）：
- Open-Meteo に、天気と一緒に昼か夜か（`is_day`）も聞く。今の天気と、歩いた時刻の天気の両方。前に保存した天気（`is_day` が無い）は昼として読む
- 晴れの夜は、太陽の代わりに、夜の空の色・ゆっくりまたたく星・月を出す。ほかの天気の夜は、雲で月は見えないので、空の色と雲の色だけ夜にする
- 月は**ふだんは三日月**で、**本当の満月の前後 1 日だけ満月**にする。満月かどうかは日付から計算する（`core/weather/Moon`。月の満ち欠けの平均の周期で計算し、通信はしない）。記録とみんなは今日、コレクションはそのパーツを歩いた日で決める
- 見た目は、太陽（白く飛んだまん中と、ふちを作らないまぶしさ）に合わせて写真に近くする：海とクレーターのある面、光と影の境のぼかし、三日月の欠けた側のうっすらとした照り返し（地球の光）
- 場所は、太陽と同じ右上だと、上の電池などの表示や、記録画面の「0 m」・歯車にかかる（ダークの満月だと字が読めない）ので、上の時計と電池のあいだの空いている所にする。大きさは半径 32dp
- 月の面は細かいので、最初に 1 枚の絵に描いておき、毎コマはその絵を置くだけにする（描き直しの重さは太陽と変わらない）

**やらなかったこと**：
- 本当の満ち欠けをそのまま出す案：半月やふくらんだ月は、小さな絵だと月と分かりにくかった
- 天気アプリの絵のような、丸をくり抜いた三日月と、丸い模様の満月：太陽が写真に近いので、並べると統一感がなかった
- 雨・くもりの夜に月を出す案：雲の下なので出さない

**AI の提案との関係**：夜に月を出す作り、三日月を基本にして満月の夜だけ満月にする案、場所、描き方は Claude Code の案。月を出すこと、三日月を基本にすること、大きさ、写真に近い見た目にそろえることは、B がエミュレータで見て決めた。


### 35. 発表用に、見本の出し入れと見せる天気を設定で選べるようにする 〔決定〕2026-11-08

**背景**：天気（道の色・アイコン・背景・滑りやすさ）や月、パーツの大きさを発表で見せたいが、本当の天気はその日しだいで、見本の天気も 5 つ（快晴・くもり・雨・晴れ・雪）しかなかった。B が「デモのデータを整理して、天気と見本をデモ用に入れておける設定にしたい」と考えた。

**決めたこと**（B）：
- 設定に「デモ」の欄を作る（デモ用に別のアプリを作るのではなく、1 つのアプリで切り替える。最初は「デモ（発表用）」にしていたが、B が見て「（発表用）」は要らないとした）
- **見本のパーツ**（出す・出さない）：オフにすると見本を全部外し、オンにすると全部戻す（「見本を戻す」と同じ）。記録したパーツには触らない。見本が 1 本でもあればオンと出す
- **デモの天気**：本当の天気（ふだん）・晴れ・晴れの夜（三日月）・晴れの夜（満月）・くもり・霧・霧雨・雨・雷雨・雪。選ぶと、記録とみんなの背景（今の天気）と、デモ散歩でできるパーツの天気がそれになる（パーツには本当の天気を聞きに行かない）。満月を選ぶと、どの画面の月も満月にする
- 見本を 7 本にし、7 つの天気が 1 本ずつになるようにした（棒：晴れ、L 字：くもり、U 字：雨、輪：霧、ジグザグ：雪、短い L 字「となりの角まで」：霧雨、長い棒「土手をずっと歩く」：雷雨）。新しい 2 本は 165 m と 1.6 km で、積むときの大きさの違い（34）も見られる。デモ散歩でも 7 本を流せる
- 前から使っている端末には、新しい見本 2 本は自動では入らない（わざと消した見本を勝手に戻さないため）。「見本のパーツ」をオフ→オン、または「見本を戻す」で入る
- **発表が終わったら消せるように、スイッチを 1 つにまとめた**（`data/AppSettings.kt` の `DEMO_SETTINGS`）。false にすると、設定の欄が出なくなり、保存してあるデモの天気も読まない（選んだまま欄を消すと、その端末が戻せなくなるため）。見本の 7 本はそのまま残る
- あわせて、記録のあとの窓の図にも天気（道の色・アイコン）を出すようにした（注記には天気が出ていたが、図はいつもの色だった）

**やらなかったこと**：デモ用に別のビルドを作る案（2 種類のアプリを作って入れ分ける手間がかかる）。背景の天気とデモ散歩の天気を別々に選ぶ案（発表で別々にしたい場面がなく、項目が増えるだけなので 1 つにまとめた）。

**AI の提案との関係**：設定の作り（見本は外す・戻すで切り替える、デモの天気を 1 つにまとめる、パーツには天気を場所より先に入れて本当の天気を聞かせない）と、新しい見本 2 本の形と長さは Claude Code の案。設定で切り替える形、天気で見せたいこと（背景・デモ散歩・見本の 7 天気）、見本の出し入れと中身の整理は B が決めた。

  - B：iPhone で歩くための記録用ページ、実データでの変換の比べ方（表と画像）、コレクション画面の実装とテスト、見た目の案の描き比べ、物理の実験（18）、エミュレータで指の動きを再現した確認（`adb shell input motionevent`）、PR とレビューの下書き
- **人が決めたこと**：保存先や命名の仕様は、AI の案を叩き台にしてチームで決めた。命名の仕様（5〜8）は、B の意見で AI の当初の計画を変えている
  - コレクション画面の方針（13・15〜17）は、AI が出した案や作った画面を B が実際に見て・触って決めた
- **鵜呑みにしなかった例**：
  - 命名の失敗時の返し方（7）：AI の「種類名を返す」案は、アプリの付け直しの流れと合わないので変えた
  - 一言コメント（6）：AI の提案は揺れたが、画面の広さという現場の事情で決めた
  - 動作確認（12）：AI の最初の確認は、古いサーバに届いていて無効だった。保存先をログに出し、別の方法でも確かめるようにした
  - モデル選び（10）：最初の予定のモデルは実際には使えなかった。AI が立てた「起動直後だけ遅い」という仮説も、直接呼んだ結果と比べて外れていると分かり、入れた仕組みを取り除いた
  - 並べ替え（16）：AI の「メニューで先頭へ」は、B が使ってみて不便だったので、iPhone と同じ操作に作り直した
  - 見出し（17）：AI のオドメーター風の案は、実際の画面で見て統一感がないので採らなかった
  - 確かめていないことは書かない（14）：AI が #13 の説明に書いた「精度に合わせる方が、潰れ方が穏やか」は、試したのがまっすぐな道だけで裏付けがなかった。消して「角のある道では未確認」と書き直した
