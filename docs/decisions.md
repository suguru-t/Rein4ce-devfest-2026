## サーバ（C）

### 1. タワーの保存先を Firestore にする 〔決定〕2026-11-06

**背景**：最初はサーバのメモリに保存していた。Cloud Run はインスタンスが入れ替わる・複数立つので、送ったタワーが消えたり、見る人によって「みんな」の一覧が違ったりする。デモ中に起きると致命的。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Firestore（採用）** | サーバレスで Cloud Run と相性がよい。サービスアカウントで接続でき鍵ファイル不要。無料枠で足りる | 一覧の並べ替えや件数に、クエリの書き方の工夫が要る |
| メモリのまま | 何もしなくてよい | 再起動・スケールで消える。デモで事故る |
| Cloud SQL | SQL で自由に集計できる | 常時起動で料金がかかる（クレジットが少ない）。設定が重い |
| Cloud Storage に JSON を置く | 単純 | 一覧・新しい順の取得が面倒。同時書き込みに弱い |

**理由**：開発前の方針（PDF 2 章）でも Firestore と決めていた。実装してみて、ルートやアプリ側を変えずに置き換えられることを確かめた。

### 2. Firestore には「タワー全体の JSON」と「一覧用の項目」を両方持たせる 〔決定〕

**決めたこと**：1 タワー 1 ドキュメント。`json` フィールドにタワー全体（`:core` の `Tower` をそのまま文字列化）を入れ、一覧用に `height`・`partCount`・`createdAt`・`author` も別に持つ。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **JSON ＋一覧用の項目（採用）** | 形式の正が `:core` の 1 か所だけ。`Part` に欄が増えてもサーバの変更が要らない。一覧は軽い項目だけ読める | Firestore のコンソールでパーツの中身が読みにくい |
| 全部を Firestore の項目に分解 | コンソールで見やすい。中身で検索できる | `Part` を変えるたびにサーバの変換コードも直す必要があり、ずれやすい |

**理由**：データ形式はチーム全員で守る約束（README「データ形式」）なので、変換の書き直しが起きる場所を増やしたくなかった。パーツの中身で検索する予定はない。

### 3. 保存先は環境で自動的に切り替える 〔決定〕

**決めたこと**：Cloud Run 上（環境変数 `K_SERVICE` がある）では Firestore、手元ではメモリ。`TOWER_STORE=firestore|memory` で明示もできる。テストは必ずメモリ版を使う。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **自動切り替え（採用）** | gcloud を入れていないメンバーの手元でも今までどおり動く。本番は設定なしで Firestore | 「今どっちで動いているか」が分かりにくい → 起動ログに `TowerStore: ...` を出して対策 |
| いつも Firestore | 本番と手元が同じ | 全員に gcloud と認証が必要。テストが本物につながってしまう |
| Firestore エミュレータ | 本物に近いものを手元で使える | 準備（Java 版エミュレータの起動など）が全員に要る |

**理由**：4 人それぞれの手元の環境をそろえる時間がハッカソンにはない。サーバ担当以外がサーバを動かすときに詰まらないことを優先した。

### 4. 命名（Gemini）は Vertex AI 経由で呼ぶ 〔決定・実装中〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Vertex AI（サーバから呼ぶ。採用）** | ハッカソンのクレジットの対象。サービスアカウントで認証でき、API キーがアプリに入らない | GCP の設定（API 有効化・権限付与）が要る |
| AI Studio（Gemini API キー） | 設定が簡単 | **クレジットの対象外**。キーの管理が要る |
| アプリから直接呼ぶ（Firebase AI Logic など） | サーバを経由しない分速い | アプリに Firebase SDK を入れない方針（PDF 2 章）に反する |

**理由**：クレジットの対象かどうかが決め手。サーバ経由なら、失敗してもアプリ側の動きを変えずに済む。

### 5. 命名を付けるタイミングと担当 〔決定〕チームで相談

**決めたこと**：採集が終わった直後に自動で付ける。API を呼ぶのは A（採集画面）、名前をパーツに保存するのと、手持ち画面の「名前を付ける」ボタン（付け直し）は B、API は C。

**理由（B の意見）**：「パーツができました」の画面で名前が出るのが一番楽しく、デモで見せやすい。ただしパーツはすぐ出して、名前は届いたら差し替える（届くまでは「名前を考え中…」）。

**実装（2026-11-07）**：A が作業できなくなったので、A の分（採集画面から API を呼ぶ）も B が作った。
- 採集の直後：結果のダイアログに「名前を考え中…」と出し、名前が届いたら保存して差し替える。付かなければ「○ m の散歩」のままにして「名前はコレクションから・あとで付けられます」と添える（7）。届くまでのあいだに自分で名前を付けていたら、そちらを残す
- コレクションの「名前を付ける」：「AI に考えてもらう」で AI の案を入力欄に入れる。保存するか・直すかは自分で決める
- 送るのは形・距離・日時だけ。今付いている名前も送らない（8）。本番のサーバで 10 回試して、どれも 1 秒ほどで返った

### 6. 命名は「名前だけ」にする（一言コメントは付けない） 〔決定〕チームで相談

**開発前の方針（PDF 4 章）からの変更**：PDF では「名前と一言」を返す予定だった。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **名前だけ（採用）** | `Part` の形を変えずに済み、全員への周知が要らない | AI らしさは少し弱まる |
| 名前＋一言 | デモで「AI が道に物語を付けた」と見せられる | 手持ちのカードが狭く、一言が入りきらない（B の指摘） |

**理由**：表示する場所がないものを作っても意味がない。一言は、あとから `Part` に空でもよい欄として足せば今までのデータもそのまま読めるので、余裕があれば後でやる。

**AI の提案との関係**：Claude Code は最初「名前だけ」を勧め、次に「`comment` 欄を足しておくのが安い」と提案を変えた。最終的には B が画面の都合から「名前だけ」を選んだ。

### 7. 命名に失敗したら 503 を返す（代わりの名前は返さない） 〔決定〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **503 を返す（採用）** | アプリは「失敗した」と分かるので、今の表示（例：「341 m の散歩」）を残し、あとで付け直せる | アプリ側に失敗時の処理が要る |
| 代わりに種類名（「ジグザグ」など）を名前として返す | アプリは何も考えずに表示できる | アプリはそれを本物の名前だと思って保存してしまい、付け直しのきっかけがなくなる |

**AI の提案との関係**：Claude Code の最初の計画は「失敗したら種類名を返す」だった。B の「失敗したら今の表示のままにして、ボタンで付け直す」という案を受けて、代わりの名前を返すと付け直しの流れが壊れることに気づき、503 に変えた。

### 8. 名前の手がかりは形・距離・日時だけ。地名は入れない 〔決定〕チームで相談

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **形・距離・日時だけ（採用）** | 位置情報がサーバに出ない（PDF 5 章のルールのまま） | 「駅前の〜」のような名前は付けられない |
| スマホ側で町名に変えて送る | 場所らしい名前が付く | 名前は共有ページ（誰でも見られる）に載るので、どこを歩いたか・どこに住んでいるかの見当がつく |
| 生の GPS をサーバに送る | 何でもできる | ルール違反。プライバシーの問題が一番大きい |

**理由**：名前は共有ページや「みんな」の一覧に出る。地名が入ると、歩いた場所が他人に知られてしまう。B が「場所を入れるならルールを変える話になる」と指摘し、今回は入れないと決めた。

### 9. 命名の安全策：3 秒で打ち切り、10 文字まで、変な入力は 400 〔決定〕

- **3 秒で打ち切る**：アプリの「名前を考え中…」が長すぎないように。時間切れは失敗（503）
- **10 文字まで**：手持ちのカードに収まる長さ。Gemini は指示より長く返すことがある。**追記（2026-11-07）**：当初はサーバで切り詰めていたが、「夕暮れの七曲りブロッ」のように言葉の途中で切れた名前が出た（#53 で B が発見）。今は、指示文で「8 文字くらい、長くても 10 文字」と余裕を持たせ、それでも超えたら前の案を見せて 1 回だけ聞き直し、まだ長ければ切り詰めずに 503（アプリは「○ m の散歩」のまま。コレクションからやり直せる）。文字数は絵文字も 1 文字と数える
- **頂点が 0 個・50 個超のパーツは 400**：変換結果は 12 個程度だが、ぴったり 12 で切るとアプリ側の変換が少し多いだけで弾かれる。Gemini に大きなデータを送らないための歯止めとして、明らかにおかしい量だけ弾く
- **命名の部品（`PartNamer`）を差し替えられるようにする**：テストでは本物の Gemini を呼ばない（お金がかからず、結果が毎回同じ）。gcloud がない手元では「命名なし（503）」で動く

### 10. Gemini のモデルは `gemini-3.5-flash-lite`（global） 〔決定〕2026-11-06 試し打ちで決定

**最初の予定からの変更**：最初は `gemini-2.5-flash` を使う予定だった。実際に呼んでみて、次の結果で替えた。

| モデル（場所） | 結果 | 判断 |
|---|---|---|
| `gemini-2.5-flash` | このプロジェクトでは **404**（モデル一覧には出るが、新しいプロジェクトからは使えない）。東京・global・米国どこでも同じ | 使えない |
| `gemini-3.8-flash`（global） | 1.5〜20 秒。英語の返事や空の返事が混ざる | 遅く不安定 |
| `gemini-3.5-flash`（東京） | 空いている時間は 0.7〜1.2 秒で名前もよい。**混む時間は 5〜8 秒、429（混雑）も返した** | 時間帯で揺れる |
| **`gemini-3.5-flash-lite`（global。採用）** | **12 回とも 0.8〜1.5 秒**。名前の質も十分（「黄昏の折り目」「初夏を刺す直進」「冬夜のループ」） | 採用 |
| `gemini-3.1-flash-lite`（global） | 速いが、10 文字を超える・記号が混ざることが多い | 不採用 |

**理由**：命名は短い仕事なので、大きいモデルの賢さより、**いつ呼んでも 3 秒以内に返ること**を優先した。3.5-flash-lite は東京にはなく global でだけ使えるが、それでも 1 秒前後で返る。

**呼び方**：
- 考える時間（thinking）は最小（`MINIMAL`）。長く考えさせると 3 秒を超える
- 返事は JSON（`{"name": "..."}`）に固定して、読み取りを安定させる
- 温度は 1.0。1.8 に上げても名前のばらつきはあまり増えなかった。代わりに指示文に「ありがちな名前は避け、意外性のある言葉選びにする」を足した（同じ特徴の散歩に毎回同じ名前が付くのを減らすため）
- 日時は日本時間の季節（「晩秋」など）と時間帯（「夕方」など）に直して渡す
- モデルと場所は環境変数（`GEMINI_MODEL` / `GEMINI_LOCATION`）で替えられる。混雑の状況が変わったら試し直す

**途中で外れた仮説**：最初、「サーバ経由だと起動直後だけ遅い」と考え、起動時に準備の呼び出しをする仕組みを入れた。ところが同じ時間に直接呼んでも遅く、遅かったのは **Gemini 側の混雑**だったと分かったので、その仕組みは取り除いた（教訓は 12 番と同じ：比べる相手を用意して確かめる）。

## 開発の進め方

### 11. main には直接入れず、PR とレビューを通す 〔決定〕チームの約束

**決めたこと**：作業ごとにブランチを切り、PR を作って、D（GitHub: mintBomber）にレビューしてもらってからマージする。PR では GitHub Actions がビルドとテストを自動で確認する。

### 12. 確認は「本当にそこにつながっているか」まで見る 〔教訓〕

Firestore 版を手元で試したとき、前に起動したサーバのプロセスが止まりきらずに残っていて、リクエストが**古いメモリ版に届いていた**。応答は正常に見えたので、気づかずに「動いた」と判断しかけた。

**対策**：起動ログに保存先（`TowerStore: FirestoreTowerStore`）を出すようにした。確認のときは、Firestore 側にも本当にデータが入ったかを別の方法（REST API）で見る。

## 変換・コレクション（B）

### 13. パーツは「分類した型」ではなく「歩いた形そのもの」で見せる 〔決定〕2026-11-06（#8）

**背景**：パーツの形はもともと軌跡の頂点から作っていて、物理もその形で動いていた。ただ、簡略化が粗く（15 m 未満の曲がりは無視、角は最大 12 個）、名前のないパーツを「U字」などの分類名で呼んでいたので、「型に当てはめられた」ように見えていた。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **歩いた形そのもの（採用）** | 自分が歩いた道だと分かる。同じ L 字でも 1 本ずつ形が違い、集める楽しさになる | 頂点が増える（上限 12 → 24 個）ので、物理の部品も増える |
| 棒・L字・U字…の型に当てはめる | 形がそろうので、積みやすさを調整しやすい | どこを歩いても似た形になり、歩いた意味が薄れる |

**決めたこと**：
- 簡略化の ε を 15 m → 8 m、頂点の上限を 12 → 24 個にした（`ConversionParams`）
- 名前のないパーツは、分類名ではなく「341 m の散歩」のように距離で呼ぶ（`Part.displayName`）
- 分類は名札と色にだけ使い、以前と同じ粗さ（15 m・12 個）で判定する。形を細かく残しても、分類と色は変わらない
- そのため、最初の予定にあった「分類（`classify`）の精度を上げる」は優先度を下げた

**理由**：B が「型に当てはまるより、歩いた形がそのまま出る方が面白い」と考えた。合わなければ戻せるように、細かさと呼び名を別々のコミットにして出した。頂点の上限はチーム共通のデータ形式なので、PR で全員に影響を書いて伝えた（D は物理の部品が増える、C はサーバの変更なし）。

### 14. 簡略化の細かさ（ε）を GPS の精度に合わせて変える 〔決定〕2026-11-06（#13）

**背景**：#8 のレビューで A から「ε 8 m だと、GPS の揺れで形がギザギザにならないか」と聞かれた。机の上で考えるより実データで確かめることにして、B が iPhone で 7 本歩き、アプリと同じ処理（`TrackFileParser` → `TrackToPart`）で変換して比べた（200 m 未満でパーツにならない 1 本を除く 6 本）。

| 案 | 結果（頂点の数） | 判断 |
|---|---|---|
| ε 8 m 固定（#8 のまま） | 精度が良い 5 本（±2.5〜3.4 m）はギザギザなし。GPS が粗い 1 本（±17〜24 m）は 16 個で、揺れが絡まる | 粗い記録に弱い |
| ε 8 m ＋ 位置を 8 m ごとに間引く | 揺れの分だけ距離が短く測られ、201 m の散歩が 200 m を割って**パーツにならなくなった**。頂点もかえって増えた（16 → 18 など） | 逆効果 |
| **ε ＝ 8 m と「使う点の精度の中央値」の大きい方（採用）** | 精度が良い 5 本は #8 と**まったく同じ**。粗い 1 本だけ 16 → **9 個** | 採用 |

**理由**：精度が良い記録の形はそのまま残し、粗い記録だけを大まかにまとめられる。精度が分からない点（GPX など）は数えず、全部分からなければ基準の ε のまま。比べた結果の表と画像は #8 のコメントにある。
**そのあとの変更**：基準の ε は、A の調整（#15）で 8 m → 10 m になった。
**位置情報の扱い**：歩いたデータはリポジトリに入れていない。比べるときも、場所を千住キャンパスに移したデータだけを共有した（自宅の近くが分からないように）。

### 15. コレクション画面の見た目は「測量野帳」 〔決定〕2026-11-06（#17）

**背景**：標準の部品のままだと、どのアプリにもある見た目で「AI で作った感じ」が出ていた。このアプリらしい見た目にしたかった。

実際のデータで 3 案を描き比べた。

| 案 | 特徴 | 判断 |
|---|---|---|
| 標本箱 | 博物館の標本のように、形を墨一色で並べる。採集番号と日時のラベル | 世界観は伝わるが、選ばなかった |
| **測量野帳（採用）** | 方眼紙に、地図の道路のような縁取りの線で描く。縮尺（実際に歩いた距離から計算）と北を入れ、「本当に歩いた道」だと分かるようにする | B が「可愛い」と感じた |
| 積み木 | パーツを色付きの立体の積み木に見せる。ゲームらしく楽しい | いちばん「よくあるゲームアプリ」に寄りやすい |

**理由**：縮尺と北を入れると「歩いた形そのもの」（13）が引き立つ。道の形と太さは物理と同じ `PartGeometry` で描くので、積む画面での当たり判定とも一致する。
**そのあと（#21）**：北の印を赤い方位磁針の針にした。パーツは 1 本ずつ白い紙片に載せて、隣との境目を分かりやすくした。アプリ全体を野帳にそろえる案は、チームで相談中（A は賛成）。

### 16. 並べ替えは、iPhone のホーム画面と同じ操作にする 〔決定〕2026-11-06（#20 → #21）

**経緯**：最初（#20）は、長押しのメニューで「先頭へ」を選ぶ形にした。ドラッグはタップ（選ぶ）や長押しとぶつかりやすく、作る手間もかかると考えたため。B が使ってみて「ドラッグで好きな場所に置ける方が便利。iPhone のアプリを移動させるときの感じにしたい」と判断し、作り直した（#21）。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| 長押しのメニューで「先頭へ」（#20） | 作るのが簡単。タップとぶつからない | 好きな場所に置けない。並べたい順にするには、何度も「先頭へ」を押す |

### 20. 歩き以外（車・自転車・走り）はパーツにしない 〔決定〕2026-11-07

**背景**：このアプリは「歩いた道」を集めるものだが、車や電車で移動しながら記録しても距離の長いパーツができてしまう。A が「歩きのときだけに限定したい」と考えた。

**決めたこと**：GPS の点列を 30 秒の窓で見て（窓の始点から終点までの直線距離 ÷ 時間）、時速 8 km（2.2 m/s）を超える区間が 1 つでもあれば「歩くより速い移動がありました」としてパーツにしない（`TrackToPart.Result.TooFast`）。記録中も最近 30 秒の速さを見て、超えていれば状態行で「速すぎます」と知らせる。

**理由**：
- 歩きは時速 4〜6.5 km、走りはゆっくりでも時速 8 km 以上なので、その間に線を引いた。自転車（時速 12 km〜）や車は確実に弾ける
- 点と点の間の速さは GPS の揺れでばらつく（既にある「飛び」の上限 5 m/s はその対策）ので、30 秒の窓で見る。信号で止まる・横断歩道を小走りで渡る程度では弾かれない
- 窓の中は、点をたどった道のりではなく始点と終点の直線距離で測る。道のりだと粗い GPS の揺れが全部足されて、歩きでも走りに見えてしまう（テストで ±6 m の揺れを入れると 2.2 m/s を超えた）。直線距離は曲がった分だけ少なめに出るが、車や走りは 30 秒で歩きの数倍は進むので十分に分かる
- 速い区間だけ切り取って残す案はやめた。切った前後がつながって、歩いていない直線が形に入ってしまうため
- 時刻の分からない点が混ざった軌跡（GPX の一部）は判定しない。今までどおりパーツになる

**AI の提案との関係**：上限の値と「30 秒の窓」は Claude Code の案。最初は道のりで測る実装だったが、既にあった粗い GPS のテストが「走り」として弾かれて気づき、直線距離に変えた。A の「歩きだけ」という方針を受けて、走りとの境目をどこに置くかを歩き・走りの一般的な速さから決めた。実機で歩いてから調整する。

**追記（2026-11-07 同日）**：A が自分で走って録った 2 本（最高 時速 8 km と 12 km）を流したところ、どちらも弾かれた。A は「ジョギングは通したい」と決め、上限を時速 8 km（2.2 m/s）から **時速 14 km（3.9 m/s）** に上げた。自転車の巡航（時速 15 km 以上）と車は弾けるが、ゆっくりの自転車は通る。
あわせて、**記録中に上限を超えたら自動で記録を止める**ようにした（`TrackRecorder`。画面を閉じていても効く）。速かった最後の 30 秒を切り落とし、そこまでの分がパーツにできる長さならパーツにする（歩いてから電車に乗った、のような場合に歩いた分を無駄にしないため）。短ければ「短すぎてパーツになりません」と出す。
この判定では飛びのフィルタ（5 m/s）を通さない。車のように速い点は飛びとして全部落とされて、速さが測れなくなるため。
そのぶん、1 点だけの GPS の飛び（B が 11/6 の歩きに 90 m の飛びを 1 点入れて試したところ止まった。#47 のレビュー）で止めないよう、上限を**超えた状態が 10 秒続いたら**止めることにした。自転車や車は超え続けるので 10 秒遅れて止まるだけで、1 点の飛びは次の点で元に戻るので止まらない。切り落とす位置は「超え始めた時刻の 30 秒前」。

### 21. 歩いたときの天気で、道の色と背景を変える 〔決定〕2026-11-07

**背景**：B が「歩いた天気で、方眼紙の上に雨を降らせたい（天気アプリのように）。雨の日の道は青くしたい」と考えた。

**決めたこと**（どれも B が選んだ）：

| 決めること | 選んだもの | ほかの案 |
|---|---|---|
| 天気を持つ場所 | スマホの中の別ファイル（`parts_weather.json`）。B だけで作れる | `Part` に足す（積む画面や共有ページでも使えるが、全員の合意が要る）。あとで移せる |
| 背景に出す天気 | 見ている画面に合わせる（採集＝今の天気、コレクション＝大きく見ているパーツ、見ていなければ最後に歩いたパーツ。積む・みんなは出さない。→ #64 で「みんな」にも採集と同じ今の天気を出すようにした。聞き直しは `WeatherService` が 15 分以内なら抑えるので増えない。→ #90 で、コレクションの一覧も今の天気にし、歩いたときの天気はカードを押して大きく見ている間だけにした（B が決めた。一覧を開くたびに前の散歩の雨が降っていると、今の空と食い違って見えるため）。大きく見ている間は、拡大表示の窓の紙（図のまわり）にもその天気を降らせる（背景だけでは、窓とまわりの暗い幕に隠れて見えにくかった。図の地図の上に降らせる案は、地図が見えにくくなるので B が採らなかった） | 最後に歩いた天気だけ／今いる場所の天気だけ |
| 描く場所 | 方眼紙の上、画面の部品の下（字やボタンの邪魔をしない） | いちばん上にうすく重ねる |

- 天気は Open-Meteo（キー不要・無料）から取る。送る位置は 0.1 度（約 10 km）に丸め、歩いた正確な場所は外に出さない
- 道の色：雨のなかまは青、雪は水色、くもり・霧は灰色、晴れはいつものオレンジ。白い紙片の上で形が見えるよう、縁取りはどれも濃くする
- → 2026-11-08（#69）：色だけでは天気が分かりにくいので、パーツの図の左上（右上の北と対になる位置）に天気のアイコン（太陽・雲・霧の線・雲と雨・雲と稲妻・雪の結晶）を出す。アイコンは道と同じ色。道の中に天気の模様（雨の筋・雪の粒・雲のかたまりなど）を重ねる案も試したが、小さいカードでは何の柄か分かりにくかったので、B が見てアイコンにした
- 晴れは天気アプリの晴れの画面に寄せた（空の色、白く飛んだ太陽、ごくうすい虹色の輪、六角形のきらめき、傾けると動く）
- 天気データの出どころ：Open-Meteo のデータは CC BY 4.0 なので、コレクションの拡大表示で天気を字で出すところに「天気データ：Open-Meteo.com（CC BY 4.0）」を添える（リンク付き）。見本の天気は作り物なので付けない
- 電池：背景はずっと動くので、描き直しを抑える。ゆっくりな空（くもり・霧・晴れ）は 1 秒に 30 回、雨・雪は 60 回まで（1 秒に 120 回描ける機種でもそれ以上は描かない）。背景だけを別の層にして方眼紙は描き直さない。傾きはセンサーが変わるたびでなく、描き直すときに入れる。記録中（採集画面を開いたまま歩くことが多い）は、どの画面でも止まった絵にして傾きのセンサーも止める（A のレビューより）。エミュレータ（GPU あり）で、雨・雪の引っかかり（描くのが間に合わないコマ）は 3〜17% → ほぼ 0%、CPU は 35〜116% → 約 22% になった

**経緯**：晴れの太陽は 5 回作り直した。扇形の光の筋 → 左上の光とレンズのきらめき（太陽と分かりにくい）→ 黄色い円盤と光芒（輪の主張が強く不自然）→ 縁のない白い光 → 空の色と虹色の輪。曇りの雲も「はっきりした雲」を試したあと、最初のふんわりした雲に戻した。雪の道の色は、白い紙片と同化して見えにくかったので濃い縁取りにした。

**AI の提案との関係**：描き方（雨粒の奥行き、霧で方眼の線を隠す、傾きで動かす など）は Claude Code の案。どの見た目を採るかは、B がエミュレータで見て毎回決めた。

### 31. 落下待ちの時間切れと、送れない結果の扱い 〔決定〕2026-11-07（#41）

**背景**：積むゲームの落下待ちは「全部止まったら次へ、6 秒で打ち切り」だった。台から落ちたパーツは落ち続けて止まらないので、落ちるたびに 6 秒待っていた（手元の物理でランダムに落とすと、6 秒の打ち切りのほとんどがこれだった）。また、6 秒たつと揺れていても次へ進み、最後の 1 個ならそのまま「完成」になって送れた。完成した後も物理が動き続け、画面の高さと送る内容がずれることがあった。

**決めたこと**：

- 時間切れ（6 秒たっても止まらない）は、途中のパーツならそのまま次へ進む。最後のパーツの判定で塔全体が止まったかをもう一度確かめるので、途中で止めてゲームを動かなくするより、先へ進めるほうを選んだ
- 最後のパーツのあとに止まらなかったときは「判定できない」（`Unresolved`）にして、送信できないようにする。1 個も残らなかった結果も送らない（サーバも空のタワーは 400 で断る：23）
- 置き切った瞬間の結果（高さ・配置・残ったパーツ）を 1 つにまとめて固定し、完成の表示と送信の両方で使う。置き切ったあとは物理を止める
- 1 フレームで進める時間は 0.05 秒まで。アプリを裏に回すとゲームループを止め、戻ったときは前のフレームの時刻を捨てる（止まっていた時間が一度に入って、待ち時間だけが進むことがない）

**やらなかったこと**：待ち時間の秒数（0.8 秒・6 秒）、台の幅、摩擦などの数値の調整。#4 のほかの項目で、実機で触りながら決める

### 32. 自分のタワーは「持ち主の印」（端末の id のハッシュ）で見分ける 〔決定〕2026-11-07

**背景**：設定でニックネームを付けられるようになったが、名前はただの文字列で、同じ名前の人が 2 人いても区別できない。「みんな」で自分のタワーに「あなた」の札を出したいが、サーバには利用者を見分けるものが何も無かった。ログイン（Google アカウントなど）はハッカソンの残り時間では重い。

**決めたこと**（C）：
- アプリが端末ごとに「持ち主の印」を作る：端末の `ANDROID_ID` にアプリだけの塩を付けて SHA-256 にした 64 桁の 16 進（`data/OwnerId`）。元の id はサーバに送らない。Android 8 以降は同じ署名なら入れ直しても同じ値なので、アプリを消しても札は残る。端末を替えると変わる
- 送るタワーに `ownerId` として入れ（`Tower` に任意の項目を 1 つ足した。古いアプリは送らないので null）、一覧を取るときはヘッダ `X-Owner-Id` で送る
- サーバは印を保存するが、**どの応答にも印を入れない**。一覧は各タワーに `mine: true/false` を付けるだけ、1 基の JSON では null にして返す。返すと、同じ人のタワーを誰でもたどれてしまうため
- 形が違う印（64 桁の 16 進でない）は、送信では 400、一覧のヘッダでは無いものとして扱う
- 送信できた id はスマホの中にも残す（`data/MyTowers`）。サーバが落ちていても札が出る保険

**印の元を `ANDROID_ID` にした理由と、気をつけること**（#66 のレビューで kkambayashi が指摘）：
- Android の指針では、見た目だけの用途にはアプリの中で作った乱数の id が勧められている。乱数にすると、アプリを消して入れ直したときに「あなた」の札が消える（`allowBackup="false"` のため）
- それでも `ANDROID_ID` を元にしたのは、「入れ直しても自分のタワーが分かる」ことを C が優先したため。印はハッシュで、元の id はサーバに届かない。サーバの中では、同じ端末のタワーが同じ印でつながる（Firestore を見られる人には分かる）。札は見た目だけで、消す・直す権限には使わない
- 利用者が印を消す手段は無い。「アプリについて」の「外に送るもの」に、この印を送っていることを書いた（#66）
- 乱数の id に切り替えるなら `data/OwnerId.kt` の元の値を変えるだけで、サーバは変えなくてよい。チームで決め直すならここ

**やらなかったこと**：ログイン（時間と、位置を扱うアプリにアカウントを結び付けたくない）。印を一覧に返して端末側で比べる案（上の理由で返さない）。ニックネームで比べる案（同じ名前を区別できない）。

**AI の提案との関係**：印をハッシュにして送る・一覧には真偽だけ返す、という設計は Claude Code の案。ログインまではしないこと、入れ直しでも残る `ANDROID_ID` を元にすることは C が決めた。

### 33. 夜は太陽の代わりに月を出す（ふだんは三日月、満月の夜だけ満月） 〔決定〕2026-11-08

**背景**：背景の天気は、晴れなら昼でも夜でも太陽を出していた。夜に歩いたパーツを見たときや、夜にアプリを開いたときも太陽が出るのはおかしい、と B が気づいた。

**決めたこと**（B）：
- Open-Meteo に、天気と一緒に昼か夜か（`is_day`）も聞く。今の天気と、歩いた時刻の天気の両方。前に保存した天気（`is_day` が無い）は昼として読む
- 晴れの夜は、太陽の代わりに、夜の空の色・ゆっくりまたたく星・月を出す。ほかの天気の夜は、雲で月は見えないので、空の色と雲の色だけ夜にする
- 月は**ふだんは三日月**で、**本当の満月の前後 1 日だけ満月**にする。満月かどうかは日付から計算する（`core/weather/Moon`。月の満ち欠けの平均の周期で計算し、通信はしない）。記録とみんなは今日、コレクションはそのパーツを歩いた日で決める（→ #90 で、コレクションの一覧も今日にし、そのパーツを歩いた日は大きく見ている間だけにした）
- 見た目は、太陽（白く飛んだまん中と、ふちを作らないまぶしさ）に合わせて写真に近くする：海とクレーターのある面、光と影の境のぼかし、三日月の欠けた側のうっすらとした照り返し（地球の光）
- 場所は、太陽と同じ右上だと、上の電池などの表示や、記録画面の「0 m」・歯車にかかる（ダークの満月だと字が読めない）ので、上の時計と電池のあいだの空いている所にする。大きさは半径 32dp
- 月の面は細かいので、最初に 1 枚の絵に描いておき、毎コマはその絵を置くだけにする（描き直しの重さは太陽と変わらない）

**やらなかったこと**：
- 本当の満ち欠けをそのまま出す案：半月やふくらんだ月は、小さな絵だと月と分かりにくかった
- 天気アプリの絵のような、丸をくり抜いた三日月と、丸い模様の満月：太陽が写真に近いので、並べると統一感がなかった
- 雨・くもりの夜に月を出す案：雲の下なので出さない

**AI の提案との関係**：夜に月を出す作り、三日月を基本にして満月の夜だけ満月にする案、場所、描き方は Claude Code の案。月を出すこと、三日月を基本にすること、大きさ、写真に近い見た目にそろえることは、B がエミュレータで見て決めた。

### 34. 積むときのパーツを、歩いた距離で大きく、天気で滑りやすくする 〔決定〕2026-11-08

**背景**：パーツはどれも長辺 1 m・同じ摩擦で、どんな散歩でも積むときは同じ扱いだった。B が「長く歩いた道ほど大きく、雨や雪の日の道ほど滑りやすいと、歩いたことが積み木に効いて面白い」と考えた。大きさは、送るタワーと「みんな」の絵・共有ページにもかかるので、チームに聞いて OK をもらった（2026-11-08）。

**決めたこと（大きさ）**：
- 長く歩いた道ほど大きい（`core/physics/PartSize`）。パーツになる最短の 150 m で 0.7 倍、2 km 以上で 1.4 倍、そのあいだは距離の対数で決める（そのままの距離に比例させると、数百 m の散歩どうしがほとんど同じ大きさになるため）。450 m ほどで 1 倍。最初は 100 m で 0.7 倍にしていたが、150 m より短い道はパーツにならないので、実際には 0.8 倍より小さくならなかった
- 物理はもともと大きさを受け付けていた（`StackWorld.place` の `scale`）。積む画面で置くときに、歩いた距離から決めて渡す。置く前の影も同じ大きさで描き、上に「776 m 歩いた道 ・ 大きさ 1.1 倍」と出す
- 置き方（`Placement`）に `scale`（大きさ）を足した。前のタワーには無いので 1 として読む。「みんな」の絵（`TowerSketch`）・共有ページの SVG と PNG は、形をこの倍率で大きくしてから置く
- サーバは大きさを検査する（0.2〜5 倍の外は 400）。アプリが決める範囲より余裕を見ている
- 長く歩いた人ほど高く積みやすくなるので、ランキングにも効く（それも含めてチームの OK をもらった）

**決めたこと（滑りやすさ）**：
- 歩いたときの天気で摩擦を変える（`core/physics/Grip`）。晴れ・不明 0.7（今までどおり）、くもり 0.62、霧 0.55、霧雨 0.35、雨・雷雨 0.15、雪 0.05。くもりと霧は、晴れとほんの少しだけ違う
- パーツどうしが触れたときは、滑りやすい方の値を使う（`StackWorld` の摩擦の混ぜ方）。dyn4j の決まり（掛けて平方根）のままだと、雪のパーツでも相手（晴れのパーツ）の値に引っ張られて、ほとんど滑らなかった。晴れのパーツどうしは前と同じ
- **台との間は、どの天気のパーツでも晴れと同じ（台は滑らない）**。台はボディの印（`PLATFORM_TAG`）で見分け、接触ごとに摩擦を置き換える（`StackWorld` の `PlatformGrip`。摩擦の値で見分けると、摩擦の大きいパーツを足したときに台と間違えるため。C のレビュー）。最初は台との間も滑りやすい方の値にしていたが、D のレビュー（#71）で、雪だけで積むと 5 本とも落ちて送れない回が 5% → 30.5% に増えると分かった。台を滑らなくすると、同じ試し方（5 本ずつ 200 回）で、全部落ちる回は雪だけで 31.0% → 7.0%、雨だけで 12.5% → 8.0%、見本の天気で 10.0% → 6.5%（晴れと同じ）になった。1 回で落ちる数は雪だけで 3.92 → 3.42 本（晴れは 3.06 本）で、パーツどうしの滑りやすさは残る
- 積む画面で、はっきり滑るパーツ（霧雨・雨・雪）なら、置く前に「雪の日の道 ・ とてもすべりやすい」と出す（頭の丸は、コレクションの道と同じ天気の色）。急に滑って驚かないように
- 送るタワーには入れない（止まったあとの置き方を保存するので、共有ページの絵には要らない）
- 物理だけで試した結果：5 本続けて積むのを 120 回ずつ比べると、積めた高さは晴れ 1.34 m、雨 1.19 m、雪 0.94 m。落ちる数はあまり変わらず、滑って横に寝てしまい高く積みにくくなる。平らな所なら雪でも置ける（平らな棒の上に 168 通り落とすと、雪の U 字は 112 通り残る。晴れは 96 通り）。次のパーツまでの待ち時間も変わらない

**やらなかったこと**：大きさを距離に比例させる案（上の理由）。滑りやすさを送るタワーに入れる案（使い道がない）。

**AI の提案との関係**：大きさの決め方（対数・0.7〜1.4 倍）、置き方に大きさを足す作り、摩擦の値と混ぜ方は Claude Code の案。大きくする・滑りやすくする考えと、晴れ・くもり・霧の順に少しずつ滑るようにすることは B が決めた。値は、物理だけの試しと、エミュレータで積んで決めた。

### 37. コレクションと選ぶ窓に、並び・天気の絞り込み・お気に入りを付ける 〔決定〕2026-11-08

**背景**：パーツが増えると、長い道だけ・雪の日の道だけ・気に入った道だけを選んで積みたいときに、一覧を上から探すしかなかった。B が「コレクションと選ぶ窓で、天気で絞り込めたり、長い順に並べられたり、お気に入りを登録できると便利」と考えた。

**決めたこと**（B）：
- 一覧の上に［並び：いつもの順 ▾］［天気：すべて ▾］［☆ お気に入り］の行を置く。並びは、いつもの順（自分で並べ替えた順）・新しい順・古い順・長い順・短い順。天気は、手持ちにある天気だけを出す
- 並びと絞り込みは、コレクションと積む画面の選ぶ窓（36）で共通にして、設定に保存する（アプリを閉じても覚えている）。変えたら一覧のいちばん上から見せる。何も残らなかったら「当てはまるパーツがありません」と「絞り込みを外す」を出す
- お気に入りは、カードの右下の ☆（押すと黄色の ★）で入れたり外したりする。選ぶ窓のカードでも同じ ☆ で入れ外しできる。押したときは星だけが少し縮み（後ろの四角の波紋は出さない）、入れたときだけ星が弾んで小さな光が散る。手持ちとは別のファイル（`parts_favorites.json`）に id で保存し、パーツを消したら外す
- 長押しの並べ替えは「いつもの順」で絞り込んでいないときだけ（ほかの並びや絞り込みの途中で動かすと、どこに入ったか分からないため）。そのときは案内を「並べ替えは「いつもの順」のときだけ」にする
- 選ぶ窓は、上の端を状態バーの下で止める（パーツが多くて窓がいちばん上まで伸びると、窓を下げる取っ手がカメラの穴と重なったため）
- 選んだパーツのうち、絞り込みで隠れているものがあれば「選んだうち n 本は、絞り込みで隠れています」と「外す」を出す（コレクションの選択中と選ぶ窓。見えないパーツが数に入ったまま外せず、ほかも選べなくなるのを防ぐ。#75 の A のレビュー）
- 並べ替え中は、並びと絞り込みの行を消さずに見えなくする（消すと一覧が上に詰まり、長押しでつかんだカードが指の下からずれた）。一覧をいちばん上に戻すのは、並びや絞り込みを変えたときだけ（ほかのタブから戻ったときは、見ていた位置のまま）
- 札・☆・「絞り込みを外す」も、ほかのボタンと同じ押し心地（38）にする。札は丸い形だけが縮み、☆ は今の縮む動きに、押した瞬間の振動を足す

**やらなかったこと**：お気に入りのカードの上の端に黄色い付箋を貼る案（B が見て、要らないとした）。入れたときに端末を震わせる案。拡大画面にお気に入りを置く案（B がカードの右下を選んだ）。

**AI の提案との関係**：並びと絞り込みの行の作り、星の弾み方と光、付箋・震える案は Claude Code の案。古い順を足すこと、☆ をカードの右下に置くこと、押したときに星の形だけが応えること、選ぶ窓でも入れ外しできること、付箋を入れないことは B が決めた。

### 38. ボタンを押したときに、縮んで弾んで戻る押し心地を付ける 〔決定〕2026-11-08

**背景**：B が「今のデザインを活かしたまま、アニメーションや見た目を凝りたい。まずはボタンを押したときのエフェクトがほしい」と考えた。今のボタンは Material の波紋が出るだけで、下のタブや題字の弾む動きとそろっていなかった。

**決めたこと**：
- アプリの全ボタン（Button・OutlinedButton・TextButton・IconButton の 32 か所）に、同じ押し心地を付ける（`ui/common/PressFeel.kt` の `PressButton` など。使い方は Material と同じで、名前の頭に Press を付けるだけ）
- Material のボタンでない、自分で作ったボタンにも同じ押し心地を付ける（`Modifier.pressFeel`）：窓の下の丸い「×」「＜」、コレクションの「選択」、選ぶ丸、並べ替え中の削除の「×」、みんなの並び替えの札、下のタブ（タブは、選ばれたあとのアイコンの弾みはそのまま、押した瞬間の縮みと振動を足す）
- 「選択」と選ぶ丸は、押せる範囲を見た目より広い四角にしているので、その四角に波紋を出さず、縮む動きだけで応える（#75 のお気に入りの ☆ と同じく、丸い形のものは形だけが応える）
- 押している間は 94% に縮み、離すとバネで戻る（`spring(dampingRatio = 0.5f, stiffness = 800f)`）。一瞬のタップでも動きが見えるよう、縮み切ってから戻す
- 塗りのボタンは、押している間だけ塗りを少し濃くする（黒に 15% 寄せる。調査の青 #1F5FA8 → #1A518F）。枠線・文字のボタンは Material の波紋のまま（うっすら色が付く）
- 押した瞬間に、指へ軽く振動を返す（`HapticFeedbackType.VirtualKey`）。無効のボタンは縮みも振動もしない
- 数値は Figma で動きを試して決めた（Figma のファイル「ミチツミ ボタンの押し心地」。While pressing → Smart Animate、バネは mass 1 / stiffness 800 / damping 28）

**やらなかったこと**：大事なボタン（記録開始・置く・積む・送信）だけの特別な演出（積み木が弾ける・スタンプなど）は、共通の押し心地を実機で触ってから決める。パーツやタワーのカード、設定の行（押すと次の画面に進む・切り替わる行）は、ボタンではないので変えていない

**AI の提案との関係**：「全ボタン共通の押し心地」と「大事なボタンだけの演出」の 2 段構え、Figma のたたき台（縮む比率・色・バネ）は Claude（Cowork）の案。B が Figma で触って、この動きに決めた。ビルドと実機での振動・気持ちよさは、まだ確かめていない

### 39. 下のタブを、選ぶと動くアイコンと「しずく」にし、ボタンの押し心地もそろえる（振動は設定で切れる） 〔決定〕2026-11-08

**背景**：B が「画面を移る下のボタンをもっと工夫したい。iPhone の Liquid Glass のような動きにしたい」と考えた。今のタブは、選ぶとアイコンが弾むだけで、どのタブも同じ動きだった。「みんな」のアイコンは共有の印で、ランキングの画面だと分かりにくかった。

**決めたこと**（B）：
- タブのアイコンを、選ばれた瞬間にタブごとに動かす（`ui/TabIcons.kt`）。アプリを開いたときに選ばれているタブは動かさない
  - 記録（足跡）：足跡が 2 歩、上へ歩く（記録画面の歯車の横の足跡と同じ）
  - コレクション（鞄 → リングで綴じたノート）：表紙が左へめくれて見開きになり、方眼のページにオレンジの道が見える。選ばれている間は開いたまま
  - 積む（積み木）：上の三角が落ちてきて乗り、下が少しつぶれて弾む
  - みんな（共有の印 → トロフィー）：跳ねて、カップに光が走り、まわりに金色の小さな星
- 選択中の後ろの楕円を、Liquid Glass のように動く「しずく」にする（`ui/TabBar.kt`）。切り替えると、進む側の端が先に・後ろの端が遅れて動くので、伸びてから縮んで着く。押すとふくらみ、指でなぞると付いてきて、離した所のタブに切り替わる。押している間は、しずくの近くのアイコンが少し大きくなる。押したときと、なぞって隣のタブに移ったときに軽く振動する。指をタブバーの外へ出してから離したときと、押している途中に取り消された（戻るジェスチャーなど）ときは、切り替えない（#79 の A のレビュー）
- タブバーそのものも、押すと少しへこみ（横 3.5%・縦 5%）、離すとぷるんと戻る。なぞっている間は、指の方へ少し（6dp まで）引っぱられる
- 38 の押し心地も、同じ手ざわりにそろえる（`ui/common/PressFeel.kt`）：押すと横 95%・縦 92% に縮み（へこんだ感じ）、押したまま指を動かすと指の方へ少し（4dp まで）寄り、離すと少し行き過ぎてからぷるんと戻る（減衰比 0.5 → 0.36）。タブは、縮む代わりにしずくのふくらみで応える（なぞる操作をタブバー全体で受けるため）
- 見た目は野帳の紙に合わせて、しずくに光沢は付けない（光沢を付けると、画面から浮いて見えた）
- 振動がいらない人もいるので、設定に「振動」のオン・オフを足す（初めはオン）。設定の「見た目」の欄を「システム」に呼び変えて、そこに入れた。アプリの振動は、すべて `ui/common/Haptics.kt` の `rememberHaptics()` を通して、オフなら鳴らさない（画面の上に開く窓の中では、上で差し替えた LocalHapticFeedback が端末のものに戻ってしまうため、呼ぶ所で設定を見る）

### 42. BGM を流す（全部の画面で同じ曲。設定でオン・オフと音量） 〔決定〕2026-11-08

- あわせて、設定の説明を短くした（BGM の説明が長かったので、ほかの説明もそろえた）

**やらなかったこと**：フリー素材の曲（規約を確かめてからにする。チームで用意するかもしれない）。画面ごとに曲を変えること（積む画面は D の担当なので、相談してから）。初めはオフにすること（開いただけで雰囲気が伝わるほうを選んだ）。オン・オフだけの設定（音量を変えたい）。

### 48. BGM を 3 曲（トコトコ・ピコピコ・ウクレレ）から選べるようにする 〔決定〕2026-11-09

**背景**：B が、BGM を 3 種類くらいにして変えられるようにしたいと考えた。

**決めたこと**（B）：
- テーマのはっきり違う 3 曲にする
  - **トコトコ**（`bgm.ogg`）：はじめからある木琴の曲（88 BPM、歩く速さでゆったり）。作り直しても音は 1 点も変わらない（前のファイルと読み比べて確かめた）。はじめは「いつもの」と呼んでいたが、ほかの曲の名前（ピコピコ）とそろえ、歩くアプリらしい名前にした
  - **ピコピコ**（`bgm_chip.ogg`）：昔のゲーム機のような音（矩形波の旋律・三角波の低い音・雑音の太鼓）。140 BPM で、16 分音符の分散和音と太鼓で走る、冒険に出るような曲
  - **ウクレレ**（`bgm_ukulele.ogg`）：ウクレレの刻み（D・DU・UDU）と口笛の旋律に、ウッドベース・シェイカー・小さな手拍子。112 BPM で、晴れた日に外を歩くような曲

- 大きさは「トコトコ」にそろえる（ほかの 2 曲は平均の大きさ（RMS）を同じにし、大きいところだけを丸く抑えて -1 dB を超えないようにする）
- 曲は `tools/make_bgm.py` の `SONGS` で作る（曲ごとに乱数の種を決めて、何度作っても同じ音）。弦の音は Karplus-Strong（雑音を 1 周期ごとにならして消していく）で、4 倍細かい点で作って音程のずれを 6 セント以内にする。3 曲で 0.58 MB
- 設定の BGM の画面に「曲」の行を足す（オン・オフの下、音量の上）。「‹ 曲の名前 ›」で、この並びの順に切り替え、端まで行ったら反対の端へ回る。曲の説明は出さない（B が決めた）。押すとすぐに新しい曲の頭から流れる（音の出番はそのまま持つ）。オフのときは切り替えられない。「初期設定に戻す」は、曲も「トコトコ」に戻す。一覧の行には「トコトコ・音量 5」のように出す
- 曲を切り替えても、流す・止めるの決まり（`BgmControl`）は変えない。`BgmPlayer` が、流している途中なら新しい曲を先に作ってから同じ大きさで流し始め（作れなかったら前の曲のまま流し続ける。#93 の A のレビュー）、止めている・譲っているときは、次に流すときに新しい曲を読む

**決めるまで**（B が聞いて直した）：
1. はじめは 3 曲とも木琴で、テンポと雰囲気だけを変えた（軽やか 112 BPM・夜 66 BPM）→「あまり違いがない」
2. 楽器ごと変えて、ピコピコとオルゴール（84 BPM のワルツ）にした →「眠くなる」
3. オルゴールを 132 BPM の弾む曲にした →「歯医者で流れていそうで、歩くアプリ向きではない」
4. 3 曲目の候補として、ウクレレと口笛・アコースティックギターの指弾きを作り、聞き比べて**ウクレレ**にした

**やらなかったこと**：画面ごとに曲を変える（B は「選べるようにしたい」）。曲の説明（はじめは名前の下に出したが、B が要らないとした）。

**AI の提案との関係**：曲の違いの付け方の候補、それぞれの曲の作り（楽器・テンポ・進行・伴奏・旋律）、3 曲目の候補（ウクレレと口笛・ローファイ・アコースティックギター）、名前の候補（トコトコ・木琴・おさんぽ）は Claude Code の案。どの曲にするか・名前・「‹ ›」で切り替えて説明を出さないことは、B が聞いて決めた。

### 55. パーツの天気は、歩き始めたときの天気にする 〔決定〕2026-11-09

**背景**：B が「長く歩いて天気が変わったとき、いつの天気になるのか」と聞いた。調べると、歩き終えた時刻（最後の点の時刻。`Part.walkedAt`）・道の形のまん中の場所の天気を 1 回だけ聞いていた。雨の中を歩き始めて途中で晴れて止めると「晴れ」のパーツになり、途中の雨は道の色にも積むときの滑りやすさにも出ない。

**決めたこと**（B）：パーツの天気は、歩き始めた時刻の天気にする（いちばん長く続いた天気・いちばん荒れた天気・歩き始めの天気、の 3 案から B が選んだ）。
- 歩き始めた時刻（最初の点の時刻）を、歩いた場所（`PartPlace.startedAt`。スマホの中だけに持ち、サーバには送らない）に持つ。天気（`WeatherService`）はこの時刻で聞く。歩き始めた時台（世界時の○時台。1 時間ごとの天気の区切り）が今と同じなら「今の天気」、前の時台ならその時台の 1 時間ごとの天気。1 時間に満たない散歩でも、歩き始めが前の時台なら歩き始めの天気になる（はじめは「歩き始めて 1 時間以内なら今の天気」のままで、ふだんの散歩は結局、歩き終えたときの天気になっていた。#103 の C のレビュー）。同じ時台の中で天気が変わったときは、1 時間ごとの天気なので分からない
- 場所は今までどおり、道の形のまん中（0.1 度・約 10 km に丸める）。散歩の長さでは、歩き始めの場所とほとんど同じ区画になる
- 歩き始めた時刻を持つ前に採集したパーツは、今までどおり歩き終えた時刻の天気（もう保存してある天気は変えない）
- デモ散歩で「デモの天気」を選んでいるときと、見本のパーツは、今までどおり決まった天気

**やらなかったこと**：歩いた間の天気を全部聞いて、いちばん長く続いた天気・いちばん荒れた天気にする案（歩いた時間の分だけ聞く回数が増える）。15 分ごとの天気（Open-Meteo の `minutely_15`）で、歩き始めの 15 分の天気を聞く案（いちばん正確だが、読み取りを足す必要がある。C の案）。前に採集したパーツの天気を聞き直すこと。拡大表示の背景の月（満月かどうか）の時刻を歩き始めにそろえること（1〜2 時間のずれでは変わらない）。

**AI の提案との関係**：今の決め方の調べと 3 つの案、歩き始めた時刻を `PartPlace` に持つ作り方は Claude Code の案。どれにするかは B が決めた。

- 字を丸ゴシックで出すので、字の集め先に設定の窓・使い方・設定の選択肢の名前・名前を付ける窓を足して切り出し直した（394 字・114 KB。ほかの字の形は変わらない）
- ライトとダークの両方で見た

**やらなかったこと**：見出しを画面名と同じ積み木（`BlockWord`）にすること（「記録中は画面を消さない」など長い見出しが窓に入らない）。説明の文（です・ます）を丸ゴシックにすること（長い文は端末の字のほうが読みやすい）。記録画面の「道を 1 本集めました」などの窓（A の画面）。

**AI の提案との関係**：ポップな枠に載せること、色の印と紙のカード、ブロックの入力の部品、4 色の線の見出しは Claude Code の案。見出しを名札にしないこと、今の設定の字の色と字体は B が決めた。

### 57. API に回数制限を付け、CORS を外す 〔決定〕2026-11-10

**背景**：サーバの URL は誰でも叩ける。AI の名前（`POST /parts/name`）とニックネーム（`POST /nickname`）は 1 回ごとに Gemini の料金がかかり、続けて叩かれると $20 のクレジットに響く。決定 23 では期間とデモの規模から回数制限を見送り、`docs/security.md` の「していないこと」に「投稿と AI の API に付けることを、C と相談中（Issue #3）」と書いてあった。また、サーバには CORS を「どこからでも可」で入れていたが、ブラウザからこの API を呼ぶ画面は無かった。

**決めたこと**（C）：
- 一覧・投稿・AI の名前・AI のニックネームに、1 分あたりの回数の上限を付ける（`server/.../RateLimit.kt`）。超えたら 429 と `Retry-After`（次に通せるまでの秒数）を返す。アプリは 429 をほかの失敗と同じに扱う（名前は今の表示のまま、送信は失敗の知らせ）ので、アプリの画面は変えない
- 端末ごとと、サーバ 1 台の合計の 2 つで数える

  | API | 端末ごと（1 分） | 1 台の合計（1 分） |
  |---|---|---|
  | `POST /parts/name`（AI） | 20 | 120 |
  | `POST /nickname`（AI） | 10 | 60 |
  | `POST /towers` | 10 | 120 |
  | `GET /towers` | 60 | なし |

  - 上限は、ふつうに使って当たらない大きさ（投稿は 5 個積むのに 30 秒ほどかかる、ニックネームは「AI に考えてもらう」を押したときだけ、など）。発表の会場で全員が一度に使っても、合計に届かない
- 端末ごとは、持ち主の印（`X-Owner-Id`、決定 32）で数える。会場や大学の Wi-Fi では全員が同じ IP に見えるので、IP だけで数えると、ほかの人のぶんまで止めてしまう。そのため、アプリは AI の 2 つの API にも印を付けて送る（数えるのにだけ使い、AI には渡さない。保存もしない）。印が無いか形が違うときは、IP（Cloud Run が付ける `X-Forwarded-For` の最初）で数える
- 印は自分で作れる文字列なので、印を変えながら叩けば端末ごとの上限はすり抜けられる。合計の上限で頭打ちにして、AI の料金が膨らまないようにする
- 数えるのはサーバの台ごと（メモリの中）。Cloud Run は最大 2 台なので、実際の上限はその 2 倍まで行くが、料金を抑える目的には足りる
- 発表の直前に何かあって止めたいときは、Cloud Run の環境変数に `RATE_LIMIT=off` を入れて出し直す（`docs/deploy.md`）。起動のログに `RateLimit: on（…）` か `off` を出す
- CORS（`install(CORS) { anyHost() }`）を外す。アプリはブラウザではないので CORS は関係なく、共有ページ（`/t/{id}`）はサーバ自身が返すので同じ場所からの読み込み。「どこからでも可」のままだと、ほかのサイトが、訪問者のブラウザからこの API を叩けてしまう
- 設定の「このアプリについて」の「端末ごとの印」に、回数の数えに使うことを書き足した

**やらなかったこと**：Firestore や Redis で台をまたいで数えること（台が 2 つまでなので、メモリで足りる。数えるたびに読み書きが増える）。Cloud Armor や API Gateway（設定と料金が増える）。IP だけで数えること（会場の Wi-Fi で困る）。ブラウザの画面を作るときのための、許す場所を決めた CORS（作ることになったら、その画面の場所だけを許す）。

**AI の提案との関係**：CORS を外したときに困ること（ブラウザで別の場所から呼ぶ画面を作るときだけ）と、回数の上限の目安・端末の印で数えて合計で頭打ちにする形・`RATE_LIMIT=off` で切れるようにすることは Claude Code の案。CORS を外すことと、回数制限を入れることは C が決めた。

### 59. 積む画面も、ほかの画面と同じ方眼の紙と今の天気にする 〔決定〕2026-11-10（#107）

**背景**：積む画面だけ、地を無地の紙（テーマの背景色）で塗りつぶしていて、アプリ全体の方眼の紙と背景の天気が隠れていた。天気の側も、決定 21 で「積む・みんなには出さない」としていた（みんなは #64 で今の天気を出すようにしたが、積むは出さないままだった）。B が「積む画面だけ見た目が違う」と提案した（#107。#4 の子）。

**決めたこと**（C）：
- 積む画面の地を塗らない（`ui/game/StackScreen.kt`）。ほかの画面と同じく、アプリ全体の方眼の紙（`fieldbookGrid`）と背景の天気が透けて見える
- 背景の天気は、ホーム・記録・みんなと同じ今の天気（「デモの天気」を選んでいればそれ）。`BackdropScreen.STACK` を足した（`ui/weather/WeatherLayer.kt`・`ui/AppNav.kt`）
- 天気は画面の部品のいちばん下に描くので、積み木・台・ゴースト（これから置くパーツ）は天気の上に出る。雨や雪の粒が積み木に重なって見えることはない。塔のまわりを薄くする手当ては要らなかった
- 動きの重さ：天気の描き直しは、ほかの画面と同じ（ゆっくりな空で 1 秒に 30 回、雨・雪で 60 回まで。設定の「背景の天気の動き」で止める・出さないも選べる。記録中は止まった絵）。積み木の物理が動くのは、置いてから止まるまでの数秒だけ
- 雨・くもり・晴れ・雪を、ライトとダークで見た。「高さ」「残り」などの字は、ダークのくもりでも読めた
- 上に画面名「つむ」（記録の「みちのきろく」と同じく、ひらがな）を、コレクション・「みんな」・記録（「みちのきろく」）と同じ積み木（`BlockWord`）で出す。位置（上から 20dp）と大きさもコレクションと同じ
- 情報の段の字も、「みんな」・コレクションと同じ太い丸ゴシックにし、天気の上に直接書くので紙の色の縁取り（`SkyText`）を付けた。高さは「みんな」の「あなたの最高」と同じ形（「高さ」・オレンジの大きな数字・「m」）で、置いて高さが変わると前の値からメーターのように回る（動きを減らす設定なら、すぐ変わる）。残り・落下・歩いた道の大きさ・置き方の一言・「落下中…」・すべりやすさの札も同じ字にした。パーツの名前は人や AI が付けた字なので、端末の字体の太字（決定 56 のニックネームと同じ考え）。丸ゴシックの切り出しに積む画面を足した（394 字 → 408 字）

**やらなかったこと**：
- 塔の高さに合わせてカメラが上がるとき、方眼の線も一緒に動かすこと。方眼はアプリ全体で 1 枚（AppNav）なので、積む画面だけ動かすには、キャンバスの中に別の方眼を描き、アプリの方眼を隠す必要がある。台と塔が動くので、上がった感じは今でも出る
- 積む画面だけ天気を薄くしたり止めたりすること（ほかの画面と同じ決まりにした）
- 輪郭だけのボタン（「⟲ 15°」など）の中にも雨や雪が透けて見えるが、ボタンの面は D の部品なので変えていない。ボタン（置く・回す・やり直す・パーツを選ぶ）と完成のカードの字も、今回は変えていない

**AI の提案との関係**：地を塗るのをやめ、天気の画面の種類に「積む」を足すだけで済むこと（天気は部品の下に描くので、粒が積み木に重ならない）、方眼をカメラと一緒に動かすのは見送ることは Claude Code の案。積む画面にも天気を出すことは B の提案（#107）で、C が決めた。

## AI（Claude Code）の使い方のメモ

提出の「AI をどの場面でどう使ったか」用。

- **使った場面**：サーバのコード（Firestore 版、命名 API）とテストの作成、手元での動作確認、Gemini のモデルの比較（実際に呼んで速さと名前を比べた）、PR の作成、作業量の見積もり、この記録の下書き
  - B：iPhone で歩くための記録用ページ、実データでの変換の比べ方（表と画像）、コレクション画面の実装とテスト、見た目の案の描き比べ、物理の実験（18）、エミュレータで指の動きを再現した確認（`adb shell input motionevent`）、PR とレビューの下書き
- **人が決めたこと**：保存先や命名の仕様は、AI の案を叩き台にしてチームで決めた。命名の仕様（5〜8）は、B の意見で AI の当初の計画を変えている
  - コレクション画面の方針（13・15〜17）は、AI が出した案や作った画面を B が実際に見て・触って決めた
- **鵜呑みにしなかった例**：
  - 命名の失敗時の返し方（7）：AI の「種類名を返す」案は、アプリの付け直しの流れと合わないので変えた
  - 一言コメント（6）：AI の提案は揺れたが、画面の広さという現場の事情で決めた
  - 動作確認（12）：AI の最初の確認は、古いサーバに届いていて無効だった。保存先をログに出し、別の方法でも確かめるようにした
  - モデル選び（10）：最初の予定のモデルは実際には使えなかった。AI が立てた「起動直後だけ遅い」という仮説も、直接呼んだ結果と比べて外れていると分かり、入れた仕組みを取り除いた
  - 並べ替え（16）：AI の「メニューで先頭へ」は、B が使ってみて不便だったので、iPhone と同じ操作に作り直した
  - 見出し（17）：AI のオドメーター風の案は、実際の画面で見て統一感がないので採らなかった
  - 確かめていないことは書かない（14）：AI が #13 の説明に書いた「精度に合わせる方が、潰れ方が穏やか」は、試したのがまっすぐな道だけで裏付けがなかった。消して「角のある道では未確認」と書き直した
