## サーバ（C）

### 1. タワーの保存先を Firestore にする 〔決定〕2026-11-06

**背景**：最初はサーバのメモリに保存していた。Cloud Run はインスタンスが入れ替わる・複数立つので、送ったタワーが消えたり、見る人によって「みんな」の一覧が違ったりする。デモ中に起きると致命的。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Firestore（採用）** | サーバレスで Cloud Run と相性がよい。サービスアカウントで接続でき鍵ファイル不要。無料枠で足りる | 一覧の並べ替えや件数に、クエリの書き方の工夫が要る |
| メモリのまま | 何もしなくてよい | 再起動・スケールで消える。デモで事故る |
| Cloud SQL | SQL で自由に集計できる | 常時起動で料金がかかる（クレジットが少ない）。設定が重い |
| Cloud Storage に JSON を置く | 単純 | 一覧・新しい順の取得が面倒。同時書き込みに弱い |

**理由**：開発前の方針（PDF 2 章）でも Firestore と決めていた。実装してみて、ルートやアプリ側を変えずに置き換えられることを確かめた。

### 2. Firestore には「タワー全体の JSON」と「一覧用の項目」を両方持たせる 〔決定〕

**決めたこと**：1 タワー 1 ドキュメント。`json` フィールドにタワー全体（`:core` の `Tower` をそのまま文字列化）を入れ、一覧用に `height`・`partCount`・`createdAt`・`author` も別に持つ。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **JSON ＋一覧用の項目（採用）** | 形式の正が `:core` の 1 か所だけ。`Part` に欄が増えてもサーバの変更が要らない。一覧は軽い項目だけ読める | Firestore のコンソールでパーツの中身が読みにくい |
| 全部を Firestore の項目に分解 | コンソールで見やすい。中身で検索できる | `Part` を変えるたびにサーバの変換コードも直す必要があり、ずれやすい |

**理由**：データ形式はチーム全員で守る約束（README「データ形式」）なので、変換の書き直しが起きる場所を増やしたくなかった。パーツの中身で検索する予定はない。

### 3. 保存先は環境で自動的に切り替える 〔決定〕

**決めたこと**：Cloud Run 上（環境変数 `K_SERVICE` がある）では Firestore、手元ではメモリ。`TOWER_STORE=firestore|memory` で明示もできる。テストは必ずメモリ版を使う。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **自動切り替え（採用）** | gcloud を入れていないメンバーの手元でも今までどおり動く。本番は設定なしで Firestore | 「今どっちで動いているか」が分かりにくい → 起動ログに `TowerStore: ...` を出して対策 |
| いつも Firestore | 本番と手元が同じ | 全員に gcloud と認証が必要。テストが本物につながってしまう |
| Firestore エミュレータ | 本物に近いものを手元で使える | 準備（Java 版エミュレータの起動など）が全員に要る |

**理由**：4 人それぞれの手元の環境をそろえる時間がハッカソンにはない。サーバ担当以外がサーバを動かすときに詰まらないことを優先した。

### 4. 命名（Gemini）は Vertex AI 経由で呼ぶ 〔決定・実装中〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **Vertex AI（サーバから呼ぶ。採用）** | ハッカソンのクレジットの対象。サービスアカウントで認証でき、API キーがアプリに入らない | GCP の設定（API 有効化・権限付与）が要る |
| AI Studio（Gemini API キー） | 設定が簡単 | **クレジットの対象外**。キーの管理が要る |
| アプリから直接呼ぶ（Firebase AI Logic など） | サーバを経由しない分速い | アプリに Firebase SDK を入れない方針（PDF 2 章）に反する |

**理由**：クレジットの対象かどうかが決め手。サーバ経由なら、失敗してもアプリ側の動きを変えずに済む。

### 5. 命名を付けるタイミングと担当 〔決定〕チームで相談

**決めたこと**：採集が終わった直後に自動で付ける。API を呼ぶのは A（採集画面）、名前をパーツに保存するのと、手持ち画面の「名前を付ける」ボタン（付け直し）は B、API は C。

**理由（B の意見）**：「パーツができました」の画面で名前が出るのが一番楽しく、デモで見せやすい。ただしパーツはすぐ出して、名前は届いたら差し替える（届くまでは「名前を考え中…」）。

### 6. 命名は「名前だけ」にする（一言コメントは付けない） 〔決定〕チームで相談

**開発前の方針（PDF 4 章）からの変更**：PDF では「名前と一言」を返す予定だった。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **名前だけ（採用）** | `Part` の形を変えずに済み、全員への周知が要らない | AI らしさは少し弱まる |
| 名前＋一言 | デモで「AI が道に物語を付けた」と見せられる | 手持ちのカードが狭く、一言が入りきらない（B の指摘） |

**理由**：表示する場所がないものを作っても意味がない。一言は、あとから `Part` に空でもよい欄として足せば今までのデータもそのまま読めるので、余裕があれば後でやる。

**AI の提案との関係**：Claude Code は最初「名前だけ」を勧め、次に「`comment` 欄を足しておくのが安い」と提案を変えた。最終的には B が画面の都合から「名前だけ」を選んだ。

### 7. 命名に失敗したら 503 を返す（代わりの名前は返さない） 〔決定〕

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **503 を返す（採用）** | アプリは「失敗した」と分かるので、今の表示（例：「341 m の散歩」）を残し、あとで付け直せる | アプリ側に失敗時の処理が要る |
| 代わりに種類名（「ジグザグ」など）を名前として返す | アプリは何も考えずに表示できる | アプリはそれを本物の名前だと思って保存してしまい、付け直しのきっかけがなくなる |

**AI の提案との関係**：Claude Code の最初の計画は「失敗したら種類名を返す」だった。B の「失敗したら今の表示のままにして、ボタンで付け直す」という案を受けて、代わりの名前を返すと付け直しの流れが壊れることに気づき、503 に変えた。

### 8. 名前の手がかりは形・距離・日時だけ。地名は入れない 〔決定〕チームで相談

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **形・距離・日時だけ（採用）** | 位置情報がサーバに出ない（PDF 5 章のルールのまま） | 「駅前の〜」のような名前は付けられない |
| スマホ側で町名に変えて送る | 場所らしい名前が付く | 名前は共有ページ（誰でも見られる）に載るので、どこを歩いたか・どこに住んでいるかの見当がつく |
| 生の GPS をサーバに送る | 何でもできる | ルール違反。プライバシーの問題が一番大きい |

**理由**：名前は共有ページや「みんな」の一覧に出る。地名が入ると、歩いた場所が他人に知られてしまう。B が「場所を入れるならルールを変える話になる」と指摘し、今回は入れないと決めた。

### 9. 命名の安全策：3 秒で打ち切り、10 文字まで、変な入力は 400 〔決定〕

- **3 秒で打ち切る**：アプリの「名前を考え中…」が長すぎないように。時間切れは失敗（503）
- **10 文字まで**：手持ちのカードに収まる長さ。Gemini は指示より長く返すことがあるので、サーバで切り詰める（絵文字を途中で切らないよう、文字単位で数える）
- **頂点が 0 個・50 個超のパーツは 400**：変換結果は 12 個程度だが、ぴったり 12 で切るとアプリ側の変換が少し多いだけで弾かれる。Gemini に大きなデータを送らないための歯止めとして、明らかにおかしい量だけ弾く
- **命名の部品（`PartNamer`）を差し替えられるようにする**：テストでは本物の Gemini を呼ばない（お金がかからず、結果が毎回同じ）。gcloud がない手元では「命名なし（503）」で動く

### 10. Gemini のモデルと呼び方 〔予定〕

- モデルは `gemini-2.5-flash`（速くて安い）。**考える時間（thinking）をオフ**にする予定：オンだと答えるまで数秒かかり、3 秒の打ち切りを超えるため
- 返事は JSON（`{"name": "..."}`）で返させて、読み取りを安定させる
- 日時は日本時間の「朝・昼・夕方・夜」と「月」に直して渡す（季節感を出すため）

試し打ちで名前の雰囲気と速さを見てから決定にする。

## 開発の進め方

### 11. main には直接入れず、PR とレビューを通す 〔決定〕チームの約束

**決めたこと**：作業ごとにブランチを切り、PR を作って、D（GitHub: mintBomber）にレビューしてもらってからマージする。PR では GitHub Actions がビルドとテストを自動で確認する。

**理由**：本番（Cloud Run）に関わる変更が多く、1 人の確認だけでは見落とす。

### 12. 確認は「本当にそこにつながっているか」まで見る 〔教訓〕

Firestore 版を手元で試したとき、前に起動したサーバのプロセスが止まりきらずに残っていて、リクエストが**古いメモリ版に届いていた**。応答は正常に見えたので、気づかずに「動いた」と判断しかけた。

**対策**：起動ログに保存先（`TowerStore: FirestoreTowerStore`）を出すようにした。確認のときは、Firestore 側にも本当にデータが入ったかを別の方法（REST API）で見る。

## AI（Claude Code）の使い方のメモ

提出の「AI をどの場面でどう使ったか」用。

- **使った場面**：サーバのコード（Firestore 版、命名 API）とテストの作成、手元での動作確認、PR の作成、作業量の見積もり、この記録の下書き
- **人が決めたこと**：保存先や命名の仕様は、AI の案を叩き台にしてチームで決めた。命名の仕様（5〜8）は、B の意見で AI の当初の計画を変えている
- **鵜呑みにしなかった例**：
  - 命名の失敗時の返し方（7）：AI の「種類名を返す」案は、アプリの付け直しの流れと合わないので変えた
  - 一言コメント（6）：AI の提案は揺れたが、画面の広さという現場の事情で決めた
  - 動作確認（12）：AI の最初の確認は、古いサーバに届いていて無効だった。保存先をログに出し、別の方法でも確かめるようにした
